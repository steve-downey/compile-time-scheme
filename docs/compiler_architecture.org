* Introduction

This document details the compile-time compiler architecture for SchemePoC, a Scheme-light compiler proof-of-concept targeting C++26. Two earlier iterations built this same staged pipeline before the current rebuild: the original Scheme-light front end, =src/smd/smdscheme/=, and the Common Lisp pivot, =src/smd/smdlisp/=. Both are retired now; their architecture prose -- Phases 1 through 7, and "The Common Lisp Layer" -- moved to =docs/history/architecture-iterations.org= at step A1 of the tree-retirement plan (=tmp/plan/=), pinned against the =iteration/smdscheme-final= and =iteration/smdlisp-final= tags taken immediately before each tree leaves trunk. What remains live in this document is =smd::cl=, the current rebuild, described in "The Common Lisp Rebuild", below.

For many C++ developers, compiler jargon and functional programming idioms can feel like a completely different language. This document translates those concepts into familiar C++ terms. We are building a compiler entirely inside C++ standard constant expressions (`constexpr`).

Rather than parsing strings directly into executable code in one messy step, this compiler uses a *staged pipeline*. It breaks the problem into distinct transforming phases:

1. **Reader**: Strings -> Reader Datum Tree
2. **Elaborator**: Reader Datum Tree -> Core Semantic Tree
3. **CPS IR**: Core Semantic Tree -> Continuation-Passing Style Intermediate Representation
4. **Backend**: CPS IR -> Executable C++ Objects (Closures or Sender Graphs)

* The Common Lisp Rebuild: =smd::cl=

=smd::smdlisp= above is the pivot; =smd::cl= (=docs/cl-rebuild-plan.md=) is the rebuild that supersedes it, one pipeline stage at a time, from step R1 onward. This section records only the facts steps R2, R4 and R5 asked to have carried here -- it is not a restatement of the rebuild's plan or of =docs/divergences/=, which classifies every deliberate gap the rebuild has accepted so far.

** The evaluator is a machine, not a fold

=smd::cl::eval::machine= (step R5) evaluates the elaborator's core tree with a small-step abstract machine rather than a recursive walk. The reason is structural, not stylistic: the elaborator's three passes (Phase 3-equivalent for this tree, =docs/cl-pivot-plan.md='s D15) are folds over node indices because a fold visits every node in a fixed order, and evaluation cannot be made into one -- it visits an =if='s arms selectively, a function body once per call rather than once per node, and, past an unwind, not at all. What evaluation *is* instead is continuation-passing style with the continuations defunctionalised: a handful of =detail::k_*= frame types are the continuation constructors, a fixed-capacity frame stack is the continuation, and =machine::step= is the transition function, driven by one =foundation::trampoline= loop rather than C++ recursion.

A consequence worth stating plainly: no evaluation recursion is C++ recursion, so the depth a program may reach is a diagnosed capacity (=limits::frames=) rather than the C++ stack, at compile time as at run time -- the same discipline =limits::steps= already applies to the step count as a whole.

** D13's three channels are now a type, not a discriminator convention

Phase 6's "a sender has three completion channels" observation, above, is what decision D13 generalises to an ordinary evaluator: =smd::cl::eval::outcome= carries a value, a diagnosed =foundation::parse_error=, or an =unwind= in flight as three distinct alternatives of one type, the same way a receiver's =set_value=/=set_error=/=set_stopped= are three distinct functions.

#+transclude: [[file:../src/smd/cl/eval/outcome.hpp::8f5b0a1c-3f0e-4f6f-95b0-2a0b4a5f6c31]] :lines 2- :src cpp :end "8f5b0a1c-3f0e-4f6f-95b0-2a0b4a5f6c31 end"

This is a sharper split than the pivot's closure backends ever had (=smd::smdlisp::closure=, above): those multiplex all four of their outcomes onto one two-alternative =result= and tell the cases apart with a pair of sentinel =parse_error= messages compared by pointer identity, which is why those sentinels had to be named =inline constexpr char[]= objects rather than bare literals. None of that machinery is ported. There is nothing left to discriminate, because there is nothing left multiplexed.

The consequence Phase 6 already named for senders applies here in exactly the same shape: splitting the channels means =unwind-protect='s run-the-cleanup-on-every-exit-path property is no longer a free consequence of there being only one exit path, and has to be *reconstructed*. In this machine it is reconstructed by =detail::k_protect=, a continuation frame that intercepts all three alternatives of =outcome= and funnels them through the same cleanup sequence before re-emitting whichever one it saved.

** The interned symbol table survives into the runtime program

Decision D12's symbol table (=smd::cl::symbol::symbol_table=, step R2) is not reader-only scaffolding that a later stage discards: the same table instance that interning built is the one the evaluator resolves every variable, function-slot, and =eq= comparison against at run time (=eval::symbol_table=, step R5's alias over it in =src/smd/cl/eval/builtin.hpp=). That is only safe because the table owns its name characters outright -- interning copies a name into the table's own pool rather than storing a view into the reader's datum arena or any other caller-owned storage -- so a program built from this table is self-contained the moment elaboration finishes, with nothing left dangling once the source text and the datum tree that read it go out of scope. This is the rebuild's answer to the dangling-view failure =docs/divergences/DIV-0007= documents for the pivot's =source_literal=: R2 designed the table so that failure mode has no equivalent here, not by patching it after the fact but by never storing a borrowed view in the first place.

** =core_cons=: a deliberate exception to "lower before you add a tag"

Decision D18 asks the elaborator to lower a new form onto existing =core_tag= alternatives before adding a new one. =core::core_cons= (step R4) is the one form R4 added anyway, and the reason is worth keeping on record rather than re-deriving: the obvious lowering for quoted list data, an ordinary call to the function named =CONS=, is not merely inelegant but *wrong*. ANSI quoted data is a literal, so =(quote (1 2))='s pairs must exist independent of what a program does to the function slot of =CONS= at run time -- a program that redefines =cons= must still get ordinary pairs from its quoted lists, and =core_call{CONS}= cannot express that independence. =core_cons= is a hermetic pair constructor with no dependency on any symbol's function slot, used only by =elaborator::emit_quoted_list= (quoted data) and never by an ordinary call to =cons= (which does lower onto the =CONS= builtin, in the function slot, exactly as D18 prefers). It is the one node kind in the rebuild's core AST that decision D18's own text names as its expected exception, not a quiet violation of the rule.

** The sender backend drives the machine; it does not fork it

Decision D17 asks for a second backend over =smd::cl='s core tree, using Beman Execution, and step R7 built =smd::cl::sender::machine_sender= to be it. Two shapes were on the table. One forks =eval::machine::evaluate_subforms='s frame, so a call's arguments run as sibling senders joined by =when_all= -- the pivot's trick (=smd::smdlisp::sender::sender_eval=), minus the pointer tree the pivot needed to see the independent set at all. The other treats one whole =machine::run= as the unit a sender completes: connect a sender, and =start= drives the machine's own trampoline to completion before dispatching its =eval::outcome= onto the matching completion function.

R7 chose the second, and the argument is a concrete cost rather than a preference. =eval::machine= is single-owner state -- one frame stack, one heap, one control register, mutated in place by =step= -- so forking an argument list means either splitting that state across concurrently-started senders, which nothing in the frame design supports, or recursing through a second evaluator built for the purpose, at which point R5's whole point (no evaluation recursion is C++ recursion, so depth and step count are diagnosed capacities rather than the C++ stack -- =limits::frames=, =limits::steps=) would be rebuilt on the sender side and immediately spent: =limits::steps= defaults to 200000, and chaining that many sender continuations recursively is 200000 C++ activation records.

#+transclude: [[file:../src/smd/cl/sender/machine_sender.hpp::0c10d654-ec97-4580-9c14-aed654701bbf]] :lines 2- :src cpp :end "0c10d654-ec97-4580-9c14-aed654701bbf end"

The channel mapping is D13's, spent a second time: a value to =set_value=, a diagnosed error to =set_error=, an unwind in flight to =set_stopped=. Execution26's stopped channel is niladic, so an unwind that reaches =machine::run= uncaught -- meaning every live =block=/=catch= inside the program already had first refusal at it, per =detail::k_block='s own resume logic -- completes with no payload; there is nothing left to carry a target and a value to, and nothing downstream that still needs them. =smd::cl::sender::run_sender= (the inverse direction, a completion turned back into an =eval::outcome= for a caller that wants one) reports that case as a diagnosed error, the same choice the pivot's =to_result= makes for an unwind that reaches the top of a program.

What this shape still buys, honestly: two whole-program evaluations are genuinely independent senders -- separate machines, separate heaps, no shared mutable state -- so joining them with =when_all= is a true structural-independence claim, never a claim about evaluation order inside either program. =machine_sender.test.cpp='s ~WhenAllJoinsTwoIndependentPrograms~ is that claim and nothing stronger; R7's step brief is explicit that ANSI's left-to-right argument order (3.1.2.1.2.3) is not up for renegotiation once an argument can have an effect, and nothing here reorders one.

DIV-0015 (accepted-permanent: Beman Execution's =connect=/=start=/=sync_wait= are not constant-evaluable) means none of this is =constexpr=, unlike =eval::machine= itself; that absence is stated in the type rather than discovered only in the tests, exactly as DIV-0015 asks of a future sender component. See =docs/divergences/DIV-0016-mendler-para-rederived-for-foundation-fix.md= (2026-08-15 note) for the fuller argument against the forking shape, including why the choice was not underdetermined between the two.

** The kit: a real second target with one real client

Step R8 extracts seventeen files into =smd::kit::foundation= (=src/smd/kit/foundation/=, target =kit.foundation=): the nine =docs/cl-rebuild-plan.md= §5 named as "essentially zero drift" -- =static_vector=, =result=, =parse_error=, =source_pos=, =source_span=, =arena_box=, =functor=, =applicative=, =alternative= -- plus =foldable=, =traversable=, =monoid=, =identity=, =fold_left_short=, =trampoline=, =result_instances= and =static_vector_instances=, which decision 2 excluded on first pass and a correction from the repository owner put back. What actually shipped is narrower than §5's sentence in one direction (§ decision 3, below) and was, for one commit, narrower than the corrected standard in another (decision 2). Both gaps are worth stating rather than papering over.

*Decision 1: what is the kit's version of a diverged file.* Diffing all three copies (=smdscheme=, =forth=, and R1's =cl= union) shows six files -- =source_pos=, =source_span=, =functor=, =applicative=, =alternative=, plus =arena_box= at a handful of lines -- unchanged in substance across all three; that is §5's zero-drift signal, verified rather than assumed. Three files carry real cl-side growth: =static_vector= gained =filled=, =append_range=, =pop_back=; =result= gained =value_type=, equality, and =and_then=; =parse_error='s equality became a merged best-of (scheme's same-pointer fast path, forth's explicit null check, cl's =std::string_view= comparison in place of a hand-rolled loop). Every one of these additions is generic over the datatype and carries no Lisp-specific type in its signature, so all three travel with the extraction as a strict superset rather than staying cl-only. D14 is unaffected: =static_vector='s =Capacity= is still its own template parameter in every one of the three old copies and the new one.

#+transclude: [[file:../src/smd/kit/foundation/static_vector.hpp::049b5617-cc33-4d2f-b479-fc81fb2a62ba]] :lines 2- :src cpp :end "049b5617-cc33-4d2f-b479-fc81fb2a62ba end"

*Decision 2: where the kit's boundary is, and the standard that actually decides it.* =src/smd/cl/foundation/= originally held thirteen files the older two copies never had: =foldable=, =traversable=, =monoid=, =identity=, =node_f=, =topo_fold=, =trampoline=, =fold_left_short=, =result_instances=, =static_vector_instances=, =tagged_tree=, =tagged_tree_instances=, =tagged_tree_schemes=. §5 rules the AST-shaped ones out by name -- =node_f=, =topo_fold=, =tagged_tree*=, and by extension =tagged_tree_instances=, the adapter that gives =tagged_tree= its Foldable and Traversable instances -- and that part of the cut stands: those five name an AST type and belong with the AST, not the substrate.

The other eight -- =foldable=, =traversable=, =monoid=, =identity=, =fold_left_short=, =trampoline=, =result_instances=, =static_vector_instances= -- were first placed with the AST group on a different argument, which was wrong and is recorded here precisely because getting it wrong once is the durable lesson. The reasoning was: §5's stated test for kit membership is "generic in shape and free of language-specific types," but §5's own supporting *evidence* for the nine files that did extract cleanly was narrower than its stated test -- "two independent implementations converged with no semantic divergence" -- and neither =smdscheme= nor =compile-time-forth= had ever needed a Foldable, Traversable, Monoid, or Identity instance, so these files looked like a sample of one. That reasoning silently swapped the *test* (generic and language-agnostic) for a *proxy* (has a second implementation already been written), and the two came apart here: =compile-time-forth= has not had the algebraic refactoring done on it that =cl= has, because nobody has done that work yet, not because its `machine`/`interpreter` state has no shape a Foldable or a Traversable would fit. The absence of a second copy measured a sibling project's backlog, not this code's generality. Re-applying §5's actual test rather than the proxy: every one of these eight is generic in every type it names and free of anything from a parser, a reader, or an AST -- =foldable=/=traversable=/=monoid=/=identity= are the same CPO shape as =functor=/=applicative=/=alternative= applied to a different pair of typeclasses; =fold_left_short= and =trampoline= are algorithms over an abstract range and an abstract state machine respectively, motivated by decision D15 and by step R5's evaluator but naming neither; and =result_instances=/=static_vector_instances= adapt =result=/=static_vector= to Functor/Applicative/Foldable/Traversable, and once all four of those typeclasses and both of those datatypes live in the kit, an adapter between them is kit material by the same logic, not cl material that happens to reach into the kit. All eight move.

The lesson to keep is not "these particular eight belong in the kit" but which question to ask next time: whether a file is generic and language-agnostic is a property of the file, checkable directly. Whether a second implementation happens to exist yet is a property of some other project's schedule. The first is §5's real bar; the second was only ever meant to be corroborating evidence for it, and corroboration that has not arrived yet is not the same claim as a test that has been failed.

*Decision 3: the "third client" premise, corrected.* §5 says extraction happens "once Common Lisp is the third working client," of both =foundation/= and =parser/= (=cursor=, =parser=, =alt=, =parser_ops=). That premise holds for =foundation/='s files -- =src/smd/cl/foundation/= genuinely defines and uses all of them, so cl is a real, working, in-tree client, verified by grep across =reader=, =elaborator=, =eval=, =sender=, =symbol= and =conformance=. It does not hold for =parser/=: =src/smd/cl/reader/cursor.hpp= is a hand-written, differently-shaped type -- no =parser<F>= wrapper, no =alt= combinator, =parse_state= folded directly into the cursor rather than living beside a generic =parser= type -- and nowhere under =src/smd/cl/= defines or uses anything resembling =parser<T>=, =alt=, or =parser_ops=. R3 built a readtable-driven hand-rolled reader instead, and nothing in the plan or the divergence log records that as a deliberate rejection of the combinator style; it is simply the shape R3 chose. The practical consequence: even the diminished claim R8's brief anticipated -- "cl is at least *a* working client, even if =smdscheme= and =forth= can't be re-pointed at the kit in this repository" -- is false for =parser/= specifically. Cl is not a client of the parser combinator layer at all. §5's "third client" premise is therefore correct for =foundation/= and does not apply to =parser/=; R8 extracts the former and leaves the latter entirely alone, undiffed and unmoved, pending either a =cl= reader rewritten onto combinators or a fourth real front end that needs them. See the dated correction appended to §5 of =docs/cl-rebuild-plan.md= for the fuller argument and see =docs/divergences/DIV-0028-parser-combinator-layer-has-no-cl-client.md= for the classification.

*The mechanism: a shim, not a rename.* =smd::cl::foundation='s namespace is preserved even though these seventeen files' definitions moved, because every consumer under =src/smd/cl= reaches =foundation::X= by unqualified name relying on ordinary nested-namespace lookup (=smd::cl::foundation= is a sibling of =smd::cl::reader=, =smd::cl::eval=, etc., found by searching enclosing namespaces) -- renaming the namespace to =smd::kit= would have silently broken every one of those call sites. Instead, =src/smd/cl/foundation/result.hpp= (and its sixteen siblings) become forwarding shims: same include path, same guard, same namespace, each with a =using= for exactly the names the original header exported, now naming =smd::kit::foundation='s definitions.

No file outside =src/smd/cl/foundation/= changed to make this true -- not =reader=, =elaborator=, =eval=, =sender=, =symbol=, nor =conformance=, nor =core= -- because both of the two things a caller could depend on (the include path and the qualified name) are unchanged. Moving =result_instances.hpp= and =static_vector_instances.hpp= wholesale, rather than leaving them in cl with a namespace-reopening workaround the way the first cut did, dissolves an awkwardness rather than papering over it: once =result=/=static_vector= and their Functor/Applicative/Foldable/Traversable typeclasses are all in the same namespace, the instance's own specializations are ordinary same-namespace code again. =tagged_tree_instances.hpp= is the file that still needs the workaround, honestly, because it is the genuine case the workaround exists for: =tagged_tree= stays in cl (AST machinery, decision 2), but all three typeclasses it instantiates are now kit-owned, so all three of its specializations -- Functor, Foldable, and Traversable alike -- open =namespace smd::kit::foundation= explicitly and name =smd::cl::foundation::tagged_tree= by qualification.

The honest scope of "extract the kit" in this repository, stated plainly: one real client (=smd::cl=), not three. =smdscheme= cannot be repointed at the kit without violating the "never edit =smdscheme= in place" rule (=AGENTS.md=), and =compile-time-forth= is a separate repository this project can read but not modify. What R8 delivers is a kit-shaped tree with a working build target, a real client, and the three-way diff as evidence that the other two copies could adopt it unchanged if their own maintainers chose to -- not an actual three-tenant migration, which no single step in this repository could perform.

** =smd::cl::printer=: a printer arrives with its first oracle, not ahead of one

Between step A3's deletion of =smdlisp= and this step, the reader had no differential oracle at all -- A3 removed =reader/oracle_compare.test.cpp='s other half along with the rest of that tree, and decision D16 is explicit that a structural comparison against another implementation in this same repository, written by the same hand, was never what external authority meant anyway. =smd::cl::printer::prin1= (step A4) closes that gap: once a datum renders as text, SBCL's own =prin1= becomes available as a reader oracle.

=prin1= is a =foundation::cata_short=, not a hand-written recursive descent (=docs/cpp-rules.md=): the carrier is one node's already-rendered text, and the failure channel is the one way rendering fails -- the text would overflow the fixed-capacity buffer. The leaf variant is dispatched with a single =std::visit= and the branch tag with a =switch=, exactly as the rules permit for an algebra that does not drive its own recursion.

#+transclude: [[file:../src/smd/cl/printer/prin1.hpp::d67e6809-36c9-43c2-84cf-14f2d189aa77]] :lines 2- :src cpp :end "d67e6809-36c9-43c2-84cf-14f2d189aa77 end"

*A provisional capacity decision.* =cata_short= materialises one carrier per node, so the fold over an =MaxNodes=-node tree holds =MaxNodes * max_print_chars= bytes of rendered text at once -- 512 characters per node, which is 32 KiB at this step's test sizes and fine there. This is sized for what this step actually needed, not for a hypothetical consumer: a client wanting a much wider tree printed in full, at full node capacity, is what would justify revisiting it. Nothing here needs that yet.

*Three traps, confirmed against a real oracle rather than guessed (SBCL 2.2.9.debian).* First, quote is a list, not an apostrophe, unless the pretty printer is on: with =*print-pretty*= bound to =nil=, SBCL prints ='x= as =(QUOTE X)= and =#'car= as =(FUNCTION CAR)=, which is the ANSI-defined reading of the syntax and does not depend on a printer variable's default; =sbcl_read_print= (below) pins the variable so the comparison is stable. Second, the empty list prints as =NIL=, never as =()=. Third, a =datum_tower= renders its stored spelling while SBCL's =prin1= renders the value the spelling denotes (=#x1f= prints as =31=, =2/4= as =1/2=, =1.50= as =1.5=) -- both are right for what each one is printing, decision D19 having chosen readable-before-executable for this reader's numeric tower, so the two simply do not agree outside canonical decimal spellings. The comparison corpus is restricted to canonical decimal towers accordingly, a restriction A5 carries forward rather than a defect A5 needs to fix. A smaller fourth trap worth recording: SBCL 2.2.9 prints the space character as =#\= followed by a literal space rather than as =#\Space=, while =#\Newline= and =#\Tab= print by name -- this printer renders every character as =#\= plus the character itself, with no name table, so it agrees with SBCL on space by accident and disagrees on named characters by design; =#\Space= and friends are kept out of the compared corpus rather than chased into matching one SBCL build's character-name table.

=sbcl_read_print= reads and prints without ever evaluating, which is what distinguishes it from the pre-existing =sbcl_prin1= (evaluates a form and prints its value) that =sbcl_differential.test.cpp= already used: the reader differential in =conformance/reader_differential.test.cpp= is therefore a check on =read= and =prin1= alone, with no evaluator in the loop. Eleven source strings -- a fixnum, a symbol, a keyword, a string with an embedded quote, a character, a flat list, a nested list, the empty list, a vector, ='x=, and =1+= -- are read by this project's own reader, rendered by =prin1=, and compared against =sbcl_read_print= of the same string; =1+= is DIV-0003's whole-token classification, and this is the first time an outside implementation has confirmed a bare =1+= reads as a symbol rather than a number. Like =sbcl_differential.test.cpp=, this is a genuine runtime test with no =constexpr= twin, a member of the default suite, and SKIPs rather than fails when =sbcl= is not on =PATH=.

*A5: the reader's differential authority is SBCL now, not =smdlisp=, and the gap A3 opened is closed.* A5 broadens the eleven cases above into two tables of forty-one source strings plus a five-case error table, all checked the same way. =inherited_cases= is every input the retired =reader/oracle_compare.test.cpp= tested -- fixnums, fold-alike symbols, keywords, lists, and the quote-family entries not already excluded -- now checked against SBCL rather than against a sibling tree in this same repository; =new_coverage_cases= is syntax that comparison never could reach, because =smdlisp= never had it (D10): strings with escapes, character literals, vectors, and canonical decimal tower spellings. All forty-six cases agreed with SBCL 2.2.9.debian on first run; none needed exclusion beyond the three traps and the =#\Space= note already recorded above.

Also recorded here because it was found while broadening this file, not because anything changed: =conformance/sbcl_differential.test.cpp=, despite its name, has never compared =cl= against SBCL -- it checks SBCL's output against the corpus's own transcribed expectation strings, which validates the corpus rather than this project's evaluator (DIV-0034). The evaluator layer accordingly still has no differential against an outside authority; only the reader layer does, as of this step.

** B1: the reader splits into =detail/= headers, so later steps have somewhere to stand

=src/smd/cl/reader/read.hpp= (step R3) held eleven =Ctx=-templated functions, two public entry points, a character-name table, and two =using=-declarations in one file, which meant every step of Phase B's combinator conversion (=docs/cl-parser-scoping.md=, D27-D31) would have declared the same single file as its scope and diffed against a moving target. Step B1 splits it into eight headers under =src/smd/cl/reader/detail/= -- the directory and the =smd::cl::reader::detail= namespace agree, and none of the eight is big enough to need its own tests, so none gets one (=docs/cpp-rules.md='s promotion rule). =read.hpp= itself shrinks to an umbrella that pulls the eight in dependency order and keeps only the two public entry points, =read_datum= and =read=.

=detail/read_node_fwd.hpp= is what makes the split possible rather than merely mechanical. =read_wrapped=, =read_delimited= and =read_sharpsign= all call =read_node=, and =read_node= calls all three back -- a genuine mutual recursion across what are now separate headers. ** B2: =smd::kit::parser= is a Monad, not merely an Applicative, and =read_radix_number= is its first client

The combinator layer this repository already had (=pure=, =satisfy=, =char_p=, =map=, =lift2=, =sequence_left=/=sequence_right=, =operator|=, =alt=, =many=, =some=, =optional=) was Applicative and Alternative and had nothing named =bind=, =and_then= or =flat_map=. That sufficed for Scheme, whose reader never needs the value of one parse to choose the next, but Common Lisp's reader is context-dependent in at least four places -- =#nnR= reads a radix that then determines how the following token is read, =#\name= looks up a character name, sharpsign sub-dispatch selects on the character after =#=, and every datum position dispatches through the readtable. =lift2= fixes both of its parsers before either runs, so no Applicative composition can express any of the four. Adding =bind= is therefore the interesting part of adopting combinators here, not a bookkeeping addition alongside it.

=bind= did not have to be invented as a free function: =src/smd/kit/foundation/monad.hpp= (=ae3c33a=) already gives this repository a =derive_monad<Impl>= CRTP base, a =monad<T>= lookup variable, and a =bind= CPO, with =result<T>= registered against it in =result_instances.hpp=. =parser<F>= (=src/smd/kit/parser/parser.hpp=) is registered the same way, in =src/smd/kit/parser/parser_instances.hpp=: an =Impl= struct supplying =bind= and =pure=, an instance map wrapping it in =derive_monad<...>=, and a =monad<parser<F>>= specialization -- exactly =result_instances.hpp='s own shape, one namespace over. There is no parser-domain-specific spelling analogous to =and_then=: =parser= has no pre-existing name to hide the CPO behind, so every call site qualifies =bind= or brings it into scope with a =using= declaration, which is why =src/smd/cl/reader/detail/read_context.hpp= carries =using smd::kit::foundation::bind;= next to its pre-existing =using foundation::and_then;=.

One placement detail the step's own sketch got wrong and is worth recording so a later step does not repeat the mistake: the =monad= lookup variable lives in =smd::kit::foundation=, and =parser<F>= lives in the sibling namespace =smd::kit::parser=, not inside =smd::kit::foundation= itself the way =result<T>= does. A variable-template partial specialization must be declared in a namespace that *encloses* the primary template's namespace -- confirmed against GCC 16 directly, not merely inferred -- and =smd::kit::parser= is not an ancestor of =smd::kit::foundation=, so the specialization cannot be written from inside =namespace smd::kit::parser= even with a fully-qualified name. =src/smd/cl/foundation/tagged_tree_instances.hpp= already carries this exact shape for the same reason, one level down in this tree (=tagged_tree= stays in =cl=, its typeclasses are kit-owned): open =namespace smd::kit::foundation= explicitly and name the specialized type fully qualified. =parser_instances.hpp= does the same for =parser<F>=.

The context is threaded through every parser call as an explicit second argument, never captured. =src/smd/kit/parser/parse_context.hpp='s =parse_context= concept names that argument's role -- "an object type that is not a =cursor='" -- rather than constraining its shape, since the kit cannot require anything language-specific of a context; what it catches is a =cursor= passed where a context belongs. =no_context= exists for a parser that genuinely needs none, but is never a default template or function argument, because =cl= is the layer's only client and there is no backward compatibility to protect. The reason to thread rather than capture is lifetime safety by construction: combinators reify parsers into storable values, so a captured =Ctx&= can dangle in a way a per-call function cannot, and =docs/divergences/DIV-0007-closure-program-datum-arena-caller-owned.md= is this project's own record of paying for exactly that bug class once already.

=read_radix_number= (=src/smd/cl/reader/detail/sharpsign.hpp=) is the first real consumer, converted onto =bind= in this step: the radix parsed from the prefix decides how the following token is classified, which is precisely the shape =lift2= cannot express. =token_p=, in =src/smd/cl/reader/detail/read_context.hpp=, lifts the untouched =scan_token= into the parser layer; =read_radix_number= itself is now =bind(token_p, classify_and_add)(cur, ctx)=, where the continuation's returned parser is resumed from whatever cursor =bind= threads it -- =token_p='s own rest, supplied by the Monad instance's plumbing, never a value the continuation has to carry by hand. =scan_token= and =classify_number= are unmodified, per Phase B's standing constraint.

** B5: text -- =read_string='s loop and =read_character='s offset arithmetic

=src/smd/cl/reader/detail/text.hpp= held the reader's last raw loop after B3 and B4, other than =scan_token='s, which is out of scope for the whole series by standing rule and is still there. =read_string= accumulated into a fixed buffer with an escape flag threaded by hand through each iteration; =read_character= did two-character lookahead and then sliced the source by offset arithmetic. Neither is a loop any more: every =while= and =for= still matching a grep over the file is a word in a doc comment.

#+transclude: [[file:../src/smd/cl/reader/detail/text.hpp::4a777d67-1246-4233-bf78-73aa4c23257a]] :lines 2- :src cpp :end "4a777d67-1246-4233-bf78-73aa4c23257a end"

*=read_string= takes B4's shape, and =operator|= gets its first production caller.* The step closure driving =many_until= owns the accumulator (=datum_string contents=) and the capacity check, exactly the division of labour B4 established: =many_until= supplies only "keep asking until told to stop or handed a failure." What used to be an escape flag remembered between iterations is now an alternative inside the repeated parser -- a single escape and whatever follows it taken literally, or any character at all -- composed with =smd::kit::parser::operator|=. B4 landed =choice.hpp= with law tests only and named B7's readtable dispatch as its expected first consumer; =read_string= has none of =read_delimited='s skip-then-choose difficulty, so it composes cleanly and becomes the first production caller instead, ahead of B7.

*The stopping condition belongs to the step, which is what makes the second alternative honest.* =read_delimited= tests for its closing delimiter in its own step, ahead of the element parser, and =read_string= does the same with the closing quote. The consequence is worth stating because the obvious alternative reads plausibly and is worse: the second alternative is *any character*, not "any character that is not a quote". Testing for the quote in both places would put the literal's termination rule in two places that have to agree, and the one inside the alternative would never fire.

*=satisfy= is the primitive this wanted and could not use, for a reason worth recording.* =smd::kit::parser::satisfy= reports its failure at the cursor it was given. Both of =read_string='s diagnostics report at the *opening quote* -- the =where= its caller passed, which is behind the cursor by the whole literal -- and so does =read_character='s `"expected character after #\\"`, whose =where= is the position of the =#=. A combinator whose failure position is fixed to the cursor cannot express a caller whose diagnostic is anchored somewhere else, so both "one character or end of input" parsers here are written out rather than built from =satisfy=. That is a finding about the primitive, not about these two callers: any later converting step whose diagnostics are anchored at an opening delimiter will hit it too, and the fix -- when a second caller justifies one -- is for =satisfy= to take the position to report at, not for callers to keep re-writing it.

*Two details a rewrite drops silently, both preserved and now pinned.* A literal ending in a bare =\= is end of input, not a diagnostic of its own: the escape parser consumes the escape and then fails, and =operator|= propagates that failure instead of falling through to the "any character" alternative -- which is how it arrives carrying `"unterminated string"`, the same message the loop's =break= reached. The reason is worth stating exactly, because the obvious one is wrong. =operator|= falls through only on a failure reported at *exactly* the cursor it started from; it compares for inequality, not for order. This failure is reported at =where=, the opening quote, which is *behind* that cursor rather than past it -- four characters behind, in the bare-backslash case =reports_errors= gained here. Every diagnostic anchored at =where= therefore commits, including one that consumed nothing, and =escaped_char='s own `"single escape"` failure is deliberately reported at the cursor instead so that the choice can reach its second alternative at all. The capacity check is still =>== against =max_string_chars= *before* the append, so a literal of exactly =max_string_chars= characters fits and one more does not, reported at the opening quote rather than at the character that would not fit. Neither had a pinning test before this step: =read.test.cpp= gained =string_capacity_boundary= (both sides of the boundary, and the overflow's position) and two cases in =reports_errors= -- the bare trailing =\=, and =read_character='s own end-of-input diagnostic below.

#+transclude: [[file:../src/smd/cl/reader/detail/text.hpp::766d64ea-9ba2-46fb-a63c-b2ce52c6fe6f]] :lines 2- :src cpp :end "766d64ea-9ba2-46fb-a63c-b2ce52c6fe6f end"

*=read_character= is a =bind=, and this is what D28's exception looks like.* Whether the first character stands for itself or opens a character name depends on the character *after* it, so the second parser is chosen by the first one's result rather than fixed in advance. D28 (=docs/cl-parser-scoping.md=) asks that applicative composition stay the default and =bind= be spent only where the grammar is really context-dependent, because =lift2= says something stronger about a parser than =and_then= does and that information should not be discarded where it holds. Here it does not hold, and saying so at the site is the point: a reader that binds everywhere has thrown the distinction away, and one that binds nowhere cannot parse this. =lookup_char_name= and =named_chars= are untouched -- a table and a case-insensitive lookup over it are not parsers, and converting them would be churn.

*Where the kit was adequate, and the one thing it was asked for and did not need.* No kit primitive changed. B4's =many_until= generalised past its one caller without alteration, which was the open question this step was placed to answer. The consumed-span-returning repetition B5 was told to watch for turned out not to apply: =read_character= has no repetition in it at all, only a =bind=, and =advance_while= already returns the end cursor the name's span is measured to. The span is still offset arithmetic on the outer cursor, which the =bind='s continuation captures because a name is measured from the first character and the continuation's own cursor is already past it. Both functions are now constrained with =reader_context=, joining =read_radix_number= and =read_delimited='s step closure; nothing in the concept turned out to be missing.

** B6: forms -- the quote family becomes one =bind=, and whole-token classification is stated where it lives

Two functions, converted for opposite reasons. =read_wrapped= (=src/smd/cl/reader/detail/forms.hpp=) is the example =docs/cl-parser-scoping.md= § 1 gives for a bind written out by hand, and the shortest statement of what the preceding five steps were for. (§ 1 leads with the reader having already re-derived =parse_state= and the layer's result type under other names, and it names =read_delimited='s =has_value()= ladder as the argument for changing anything.) =read_token_datum= (=src/smd/cl/reader/detail/token_datum.hpp=) is the one place in the series where a careless combinator translation would break the behaviour the whole plan names as most at risk.

#+transclude: [[file:../src/smd/cl/reader/detail/forms.hpp::086ca303-e32b-40bb-88fd-09a2cffaad61]] :lines 2- :src cpp :end "086ca303-e32b-40bb-88fd-09a2cffaad61 end"

*=read_wrapped= was =bind= written out by hand, twice, over two monads that shared a spelling.* Both nestings were =and_then=: the inner datum's =result= feeding a branch append, the branch append's =result= feeding a =parse_state=. The outer one is now the parser Monad's =bind=, with =read_node= lifted into a =parser= value at the call; the inner one stays =result='s own =bind=, because appending to the tree is not a parse step and pretending it is would say something false about it. The line count is not the argument: at 22 lines against 18, the converted function is four lines longer than the one it replaced. What is worth having is the part that stopped being written down, the resumption cursor. It used to be =inner.rest=, spelled out by hand inside the continuation, and =bind= now threads it. =read_radix_number= made the same observation at B2; this is the first place the alternative was a *nested* hand-written bind rather than a single one.

*The two positions, and the test that now keeps them apart.* The branch is recorded at =where= -- the marker's position, passed in by =read_sharpsign= or by =read_node='s readtable dispatch -- and not at the inner datum's, which for `'x` is one character further on. Nothing in the types distinguishes them: both are =source_pos=, and =where= reaches the tree only as the position of a =datum tree full= diagnostic, so on every successful read the choice is invisible. This step's own step file named the hazard and observed that no test would say so, which was true. =read.test.cpp= gained ~wrapped_branch_error_sits_at_the_marker~: a read of =" 'x"= with room for exactly one node, where the leaf =x= fills the tree and the quote's branch is what overflows, pinning the reported column at the quote rather than past the =x=. Checked by mutation rather than by inspection -- substituting the resumption cursor's position fails the =static_assert=, so the case is not vacuous.

*=read_token_datum= is where DIV-0003 lives, and the conversion is what makes it structural.* A whole token is scanned and *then* classified, which is why =1+= reads as the symbol =1+= and not as the fixnum 1 with a stray =+= after it: Common Lisp symbols may start with a digit, so no decision taken part way through a token can be right. The converted shape is =bind(token_p, classify_and_intern)(cur, ctx)= -- the same shape =read_radix_number= has carried since B2, for the same reason -- and everything that could have gone wrong here is a shape the conversion does not take: not a =satisfy= over constituent characters, not a choice between a number parser and a symbol parser, neither of which can see the token it is half way through. The retired Scheme reader's greedy-digit integer parser is exactly the shape DIV-0003 records as wrong, and it is the shape a combinator rewrite reaches for by default, which is why the =bind= site now carries a comment saying so. =scan_token= and =classify_number= are untouched here as everywhere in Phase B; their immutability is what makes the divergence safe by construction rather than by test.

*The outside oracle ran, for the first time in this phase.* A4 and A5 built a differential that reads a corpus with =cl= and with SBCL and compares what both print, and =1+= is in it. B5 could not use it -- SBCL was not installed on the machine, the differential cases skip when it is absent, and ctest counts a skip as a pass, so a green matrix said nothing. It was reinstalled before this step. The differential ran green here at 180 assertions across three =ReaderDifferentialTest= cases (300 across five, counting the two =SbclDifferentialTest= corpora), identical to the figure on the pre-change tree, against *SBCL 2.6.0.debian*. A4 and A5 recorded their agreement against 2.2.9, so this is also the first exercise of the corpus against 2.6, and nothing in it disagrees. That is the first time this project's most load-bearing reader behaviour has been checked against something other than its own opinion within Phase B.

*Both functions are now constrained with =reader_context=*, joining =read_radix_number=, =read_string=, =read_character= and =read_delimited='s step closure. Nothing in the concept was missing, which is now four converting steps in a row that have found nothing missing in it. =read_delimited='s own =Ctx= is still a bare =class Ctx= -- only its inner step closure names the concept -- and =read_sharpsign= and =read_node= are B7's.

** B7: the readtable dispatch, and what the layer costs in constant-evaluation stack

What was left of the reader after B6 was its spine: =read_node= (=src/smd/cl/reader/detail/node.hpp=) switching on =readtable::macro_of=, and =read_sharpsign= (=src/smd/cl/reader/detail/sharpsign.hpp=) switching on =readtable::sharp_of=. Decision D19 is explicit that this lookup, and not a chain of character tests, is what the reader is built around, and it asks further that the reader be shaped so a later =set-macro-character= is a table lookup selecting among parsers rather than a redesign.

*The readtable turned out to be the easy part of adopting combinators, not the obstacle.* Because a datum is an arena index, every arm of both switches already returns =foundation::result<parse_state<int>>=. Same-typed alternatives are easier to combine than the heterogeneous =T= the retired Scheme layer dealt with, so what a readtable selects among is *already* a set of same-typed parsers; that is the structure D19 asked for, and this step is where it becomes available rather than merely imaginable. A later =set-macro-character= adds a row to a table of =parser= values. It does not touch the dispatch.

#+transclude: [[file:../src/smd/cl/reader/detail/node.hpp::b803edcd-959d-4364-94f8-13fb256e7b9b]] :lines 2- :src cpp :end "b803edcd-959d-4364-94f8-13fb256e7b9b end"

*The switches stay switches, and that is the point rather than a concession.* =operator|= searches: it tries alternatives in order and, on a double failure, reports the last one's error. A readtable selects one arm by lookup and commits to it, letting that arm's own diagnostic stand. The two differ exactly when an arm fails, which is every diagnostic in either function, so D31 -- no change to which diagnostic surfaces or where -- settles it. What changed is that each arm names a parser instead of open-coding a call.

The one place =operator|= *is* right is =read_node='s comma arm, and the distinction is worth stating because it looks like the same thing. =,@= against =,= is a lookahead between two spellings of one macro character: there is no table entry to consult, and nothing to commit to until the next character is read. The splice alternative fails at the cursor =operator|= started from whenever the =@= is absent, which is what lets the plain unquote stand; once the =@= is consumed the alternative has committed, and everything that can fail after it reports at the comma's own position or beyond, never back at the starting cursor.

#+transclude: [[file:../src/smd/cl/reader/detail/sharpsign.hpp::b3055934-2efb-4df4-a4bb-e961e29e7d0f]] :lines 2- :src cpp :end "b3055934-2efb-4df4-a4bb-e961e29e7d0f end"

*The infix numeric argument is a parser that cannot fail.* =#nnR= reads an optional digit run before dispatching, and the argument then decides which parsers the following character may name -- five of =read_sharpsign='s seven arms refuse an argument outright through the =reject_argument= guard, one requires it to be a radix between 2 and 36, and one refuses it with a message of its own. So the second parser is chosen by the first one's value, which is a =bind= rather than a =lift2=, the same exception D28 names for =read_character=. Absence of a digit is a value there and not an error, which is why =optional= is in the composition: it turns =satisfy='s own cursor-positioned failure, which no caller of this ever sees, into the =std::nullopt= that =many_until= reads as "stop".

*What the combinator layer costs, in the one currency this project has not been measuring.* Reifying a parser is not free at compile time, and the cost is not instantiation time -- it is constant-evaluation stack. The reader's recursion is ordinary C++ recursion, unlike the evaluator's, so every parser between =read_node= and its own recursive call spends =-fconstexpr-depth=, and GCC's default cap of 512 is a hard wall rather than a budget. The 64-deep nested-quote case in =src/smd/cl/printer/prin1.test.cpp= -- written by A4 to overflow the *printer's* character limit, not to stress depth -- needed 424 before this step and 570 after, and the build stopped. Converting =parser<F>= to re-export its callable's =operator()= instead of forwarding to it removes one frame from every parser invocation in the tree and brings the same case below 380. The number worth carrying forward is not 380: it is that a converted reader function costs depth proportional to source nesting, and that the margin was 88 frames when nobody was watching.

** B8: what the reader is, now that seven steps have finished converting it

B1 through B7 each converted one part of the reader and wrote down what that part taught. This section is the other thing, which none of them could write: what the reader *is* after all seven, stated once, so that the next person to open =src/smd/cl/reader/= does not have to reconstruct it from seven step records in reverse order.

*The layer is nine combinators in six headers, and it stopped growing after B4.* =src/smd/kit/parser/= holds =cursor.hpp= (=cursor= and =advance_while=, moved out of =cl= by B2 and left behind as a forwarding shim), =parse_context.hpp= (the =parse_context= concept and =no_context=), =parser.hpp= (=parser<F>=, =parse_state<T>=, =parse_result<T>=, and the primitives =pure=, =map=, =satisfy=, =char_p=), =parser_instances.hpp= (the =monad<parser<F>>= registration, whose basis is =pure= and =bind= and which carries a native =fmap=), =choice.hpp= (=operator|=, its named alias =alt=, and =optional=), and =repeat.hpp= (=skip_many= and =many_until=). B2 landed =pure=, =map= and =bind=; B3 added =satisfy=, =char_p= and =skip_many=; B4 added =operator|=/=alt=, =optional= and =many_until=. B5, B6 and B7 each converted reader functions and added nothing, which is the three-consumer evidence the provisional note in §B2 was waiting for. The one extension anybody asked for and did not get -- a position parameter on =satisfy=, so a caller can anchor a diagnostic somewhere other than the cursor -- is still unbuilt because no second caller has needed it, and the standing instruction is still to extend =satisfy= in place when one appears rather than to write a parallel primitive beside it.

*Three context types are threaded, and naming each at the signature that wants it is what keeps them apart.* =detail::read_context<SymbolTable, MaxNodes, MaxList>= carries the three things a whole read shares -- the datum tree being built, the symbol table names intern into, and the readtable every character decision is read from -- and =detail::reader_context= is the concept that names exactly those members. Every converting step constrained the functions it converted, so the concept now constrains =read_radix_number=, =read_string=, =read_character=, =read_wrapped=, =read_token_datum=, =read_sharpsign= and =read_node=, plus =read_node='s forward declaration in =detail/read_node_fwd.hpp=, which had to gain the same constraint or it would declare a different template from the definition. The second type is =readtable const= itself, threaded bare: =skip_intertoken_space= is called by the public =read<>= entry point before any =read_context= exists, and a readtable models =parse_context= directly, so there was nothing to wrap. The third is =no_context=, used in exactly one place -- =skip_detail='s two-character =#|= and =|#= matchers, which need a context parameter because =parser<F>= takes one and need nothing from it. =parse_context= excludes exactly one type, =cursor=, which is the whole of what it is for: both parameters are ordinary value-like types, so an argument-order mistake would otherwise be silent.

*The file layout is B1's, and the mutual recursion is why it works.* =read.hpp= is an umbrella holding the two public entry points, =read_datum= and =read=, and including eight headers from =src/smd/cl/reader/detail/= in dependency order: =read_context.hpp=, =skip.hpp=, =text.hpp=, =token_datum.hpp=, =forms.hpp=, =sharpsign.hpp=, =read_node_fwd.hpp= and =node.hpp=. None of the eight is large enough to need its own tests and none has one. =read_wrapped=, =read_delimited= and =read_sharpsign= all call =read_node= and =read_node= dispatches back to all three, so the forward declaration in =read_node_fwd.hpp= is not tidiness but the thing that makes the split possible: every function on both sides of the cycle is a template, so a declaration suffices at each call site and the definition need only be visible at the point of instantiation, which the umbrella's include order guarantees.

*Two places do the worse thing on purpose, because D31 said this series does not get to improve behaviour on the way past.* The first is =skip_many= and the block comment it drives. An unterminated =#|= consumes to end of input regardless of nesting depth, and the diagnostic the user sees comes from the caller's end-of-input handling rather than from the comment skipper, which is a strictly worse message than the natural recursive-combinator answer -- one pointing at the unterminated comment itself -- would be. =skip_many='s contract is built around preserving it: exhaustion of its inner parser is *success*, not failure. B3 pinned the behaviour with two new cases in =read.test.cpp=, which is the only reason it is now safe from a later step improving it by accident.

The second is =many_until= and =read_delimited='s capacity check. The natural move when hoisting a collecting repetition into a kit is to give the combinator the capacity and the container, and that was considered and refused. =read_delimited= needs its stop condition (the closing delimiter) tested ahead of its keep-going condition (one more element) on every turn, and it needs the capacity-overflow diagnostic to sit at the post-intertoken-skip position of the element that would not fit; both are exact when the step closure that already holds that cursor also owns the accumulator and the check, and both become approximate the moment collection moves into a generic combinator. So =many_until= supplies control flow and nothing else -- keep asking until told to stop or handed a failure -- and the capacity check stayed in =read_delimited='s own step, in the shape it already had. What makes the repetition a diagnosing one rather than a truncating one is therefore its caller, not itself, which is also why it is not named =many_bounded=.

*Nothing in the series changed an existing expectation.* Across B1 through B7 the whole of =src/smd/cl/**/*.test.cpp= and =src/smd/cl/conformance/= moved by one file and 56 added lines: four new =fails_with= rows and two new =constexpr= predicates in =read.test.cpp=, from B3, B5 and B6. All seventeen pre-existing =fails_with= expectations survive character for character, and the single deleted line is a statement terminator that became a conjunction so the chain could be extended. The conformance corpus was not touched at all. Each addition closed a diagnostic no test covered -- the unterminated =#|= pair, =read_character='s "expected character after #\\", a string literal ending in a bare backslash, =max_string_chars='s boundary on both sides, and =read_wrapped='s branch position -- so for those paths a green matrix had previously been proving nothing.

*** D30: what the combinator layer cost at compile time

Decision D30 asks for the compile-time price to be measured and recorded rather than gated, on the reasoning that =constexpr= here is a correctness discipline and a demonstration rather than a product feature. These numbers are therefore a record, not an argument. The one outcome that would have counted against the change is a limit that cannot be raised, and there is none.

Taken on a 13th Gen Intel Core i7-13700H (20 threads, 91 GiB), Ubuntu 26.04.1, Linux 7.0.0-30-generic, with =g++-16 (Ubuntu 16-20260322-1ubuntu1) 16.0.1 20260322 (experimental) [trunk r16-8246-g569ace1fa50]=. *Before* is =d6ae364=, the merge base of =main= and =cl-parser-combinators=, whose reader is the monolithic =read.hpp= of step R3. *After* is =633ee81=, the branch as B7 left it.

Whole =make test-matrix=, both legs, from an empty build directory with =ccache= disabled -- which matters, because the project configures =ccache= as the compiler launcher and a "cold" build that keeps it is measuring the cache:

| measurement | before | after |
|-------------+--------+-------|
| matrix wall time, cold | 65 s | 91 s |
| C++ translation units compiled | 140 | 152 |
| ctest entries per leg | 326 | 379 |

The 40% is not all conversion cost, and the two extra rows say why: all twelve extra translation units are the kit's six new test files compiled once per configuration, and all 53 extra ctest entries are theirs -- seven new suites, none of them in =cl=. The reader's own translation unit is the honest number, compiled alone with =-fsyntax-only= and the flags taken from =compile_commands.json=, three runs, minimum reported:

| =read.test.cpp= | before | after | ratio |
|-----------------+--------+-------+-------|
| =Debug= (=-O0=) | 1.62 s | 2.01 s | 1.24 |
| =Asan= (=-O3=) | 1.86 s | 2.34 s | 1.26 |

*The ops limit was never the binding one.* GCC's default =-fconstexpr-ops-limit= is 33554432, confirmed from the compiler's own diagnostic. Bisecting the smallest limit at which each translation unit still compiles:

| minimal =-fconstexpr-ops-limit= | before | after | ratio |
|---------------------------------+--------+-------+-------|
| =read.test.cpp= | 149541 | 1046872 | 7.0 |
| =prin1.test.cpp= | 3323259 | 3429007 | 1.03 |

A sevenfold increase in evaluated operations is a real constant factor, and it still leaves the reader using three percent of the default budget. The limit is a flag, and raising it is free.

*The sevenfold is not the conversion's cost, though, and saying so was the same mistake as the whole-matrix row.* The two columns above are not the same file: =read.test.cpp= gained four expectations and two =constexpr= predicates over B3, B5 and B6, and the ops limit is a property of a translation unit rather than of the reader inside it. Holding the file fixed and compiling it against both readers separates the two (bisected the same way, =-fsyntax-only -O0=, the pre-series file taken from =d6ae364= and compiling clean against the post-series headers under =-Wall -Wextra=):

| =read.test.cpp=          | before reader | after reader | ratio |
|--------------------------+---------------+--------------+-------|
| the file as B1 found it  |        149541 |       260368 |  1.74 |
| the file as B7 left it   |        208953 |      1046872 |  5.01 |

*1.74 is what the conversion costs on identical input.* The rest is one added case. =string_capacity_boundary= reads a 129-character string literal at =static_assert= to pin =max_string_chars= on both sides; comment out that one =static_assert= and the same file needs 325965 operations after against 171779 before. So that single case accounts for 720907 operations under the converted reader and 37174 under the old one, a factor of nineteen.

That is the shape of the charge, and it is worth more than the headline. =read_string= was a raw loop and is now =many_until= over =escaped_char | any_char=, reifying a parser per character, so the conversion costs operations per *character of input* where the old reader cost them per datum. Nothing else in the tree reads a long literal. The one thing that does is a test B5 added, which is why the translation-unit number reads as sevenfold and the reader's own number is under two.

*The binding limit is =-fconstexpr-depth=, and this is the finding the section exists for.* GCC caps constant-evaluation depth at 512 by default, again confirmed from the compiler's diagnostic, and the reader's recursion -- unlike the evaluator's, which is a machine -- is ordinary C++ recursion. So every reified parser between =read_node= and its own recursive call is a frame, and the cost scales with the *nesting depth of the source being read*. Bisecting the minimal depth at which each translation unit compiles:

| minimal =-fconstexpr-depth= | before | after |
|-----------------------------+--------+-------|
| =read.test.cpp= | 46 | 67 |
| =prin1.test.cpp= | 167 | 363 |

=prin1.test.cpp= is the deepest constant evaluation in the tree: A4 wrote it to read 64 nested quotes and overflow the *printer's* character limit, not to stress depth, which is why it was the case that noticed. Reading N nested quotes through =read= at =static_assert=, from a probe outside the repository, gives the shape rather than one point of it:

| nesting depth N | before | after |
|-----------------+--------+-------|
| 1 | 41 | 48 |
| 2 | 43 | 53 |
| 4 | 47 | 63 |
| 16 | 71 | 123 |
| 64 | 167 | 363 |
| 100 | 239 | 543 |

Both are linear, and exactly so: before is =39 + 2N= and after is =43 + 5N=, which is every probed value at N = 1, 2, 4, 16, 64 and 100 with nothing left over. *2.0 frames per level of source nesting before, 5.0 after* -- over a fixed overhead that is 39 frames before and 43 after, not the same on both sides. That predicts a ceiling, and the prediction holds exactly -- bisecting the deepest N that compiles at the default =-fconstexpr-depth=512= gives *236 before and 93 after*, which is what those two lines give and not what a shared overhead of 39 would have given for the second of them. The reader can read a form nested 93 deep at compile time with no flags, where it could manage 236.

*What that cost, stated plainly.* Two and a half times the stack per level of nesting, and a default-flags nesting ceiling cut to 39% of what it was. It was very nearly worse: B7's first conversion of the readtable dispatch, with =parser<F>= holding its callable and forwarding to it, put =prin1.test.cpp= at 570 and stopped the build, and the margin before that step -- with nobody measuring -- had been 88 frames. Re-exporting the callable's =operator()= instead of forwarding removed one frame from every parser invocation B2 onward had placed and brought the same case to 363. The qualitative question D30 actually asks is whether a workable limit exists, and it does: =-fconstexpr-depth= is a flag, the project sets it nowhere, and the tree compiles under the default with 149 frames to spare. A deeper source is a compiler flag away, which is exactly the kind of cost D30 says not to gate on.
