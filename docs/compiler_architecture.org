* Introduction

This document details the compile-time compiler architecture for SchemePoC, a Scheme-light compiler proof-of-concept targeting C++26. Two earlier iterations built this same staged pipeline before the current rebuild: the original Scheme-light front end, =src/smd/smdscheme/=, and the Common Lisp pivot, =src/smd/smdlisp/=. Both are retired now; their architecture prose -- Phases 1 through 7, and "The Common Lisp Layer" -- moved to =docs/history/architecture-iterations.org= at step A1 of the tree-retirement plan (=tmp/plan/=), pinned against the =iteration/smdscheme-final= and =iteration/smdlisp-final= tags taken immediately before each tree leaves trunk. What remains live in this document is =smd::cl=, the current rebuild, described in "The Common Lisp Rebuild", below.

For many C++ developers, compiler jargon and functional programming idioms can feel like a completely different language. This document translates those concepts into familiar C++ terms. We are building a compiler entirely inside C++ standard constant expressions (`constexpr`).

Rather than parsing strings directly into executable code in one messy step, this compiler uses a *staged pipeline*. It breaks the problem into distinct transforming phases:

1. **Reader**: Strings -> Reader Datum Tree
2. **Elaborator**: Reader Datum Tree -> Core Semantic Tree
3. **CPS IR**: Core Semantic Tree -> Continuation-Passing Style Intermediate Representation
4. **Backend**: CPS IR -> Executable C++ Objects (Closures or Sender Graphs)

* The Common Lisp Rebuild: =smd::cl=

=smd::smdlisp= above is the pivot; =smd::cl= (=docs/cl-rebuild-plan.md=) is the rebuild that supersedes it, one pipeline stage at a time, from step R1 onward. This section records only the facts steps R2, R4 and R5 asked to have carried here -- it is not a restatement of the rebuild's plan or of =docs/divergences/=, which classifies every deliberate gap the rebuild has accepted so far.

** The evaluator is a machine, not a fold

=smd::cl::eval::machine= (step R5) evaluates the elaborator's core tree with a small-step abstract machine rather than a recursive walk. The reason is structural, not stylistic: the elaborator's three passes (Phase 3-equivalent for this tree, =docs/cl-pivot-plan.md='s D15) are folds over node indices because a fold visits every node in a fixed order, and evaluation cannot be made into one -- it visits an =if='s arms selectively, a function body once per call rather than once per node, and, past an unwind, not at all. What evaluation *is* instead is continuation-passing style with the continuations defunctionalised: a handful of =detail::k_*= frame types are the continuation constructors, a fixed-capacity frame stack is the continuation, and =machine::step= is the transition function, driven by one =foundation::trampoline= loop rather than C++ recursion.

A consequence worth stating plainly: no evaluation recursion is C++ recursion, so the depth a program may reach is a diagnosed capacity (=limits::frames=) rather than the C++ stack, at compile time as at run time -- the same discipline =limits::steps= already applies to the step count as a whole.

** D13's three channels are now a type, not a discriminator convention

Phase 6's "a sender has three completion channels" observation, above, is what decision D13 generalises to an ordinary evaluator: =smd::cl::eval::outcome= carries a value, a diagnosed =foundation::parse_error=, or an =unwind= in flight as three distinct alternatives of one type, the same way a receiver's =set_value=/=set_error=/=set_stopped= are three distinct functions.

#+transclude: [[file:../src/smd/cl/eval/outcome.hpp::8f5b0a1c-3f0e-4f6f-95b0-2a0b4a5f6c31]] :lines 2- :src cpp :end "8f5b0a1c-3f0e-4f6f-95b0-2a0b4a5f6c31 end"

This is a sharper split than the pivot's closure backends ever had (=smd::smdlisp::closure=, above): those multiplex all four of their outcomes onto one two-alternative =result= and tell the cases apart with a pair of sentinel =parse_error= messages compared by pointer identity, which is why those sentinels had to be named =inline constexpr char[]= objects rather than bare literals. None of that machinery is ported. There is nothing left to discriminate, because there is nothing left multiplexed.

The consequence Phase 6 already named for senders applies here in exactly the same shape: splitting the channels means =unwind-protect='s run-the-cleanup-on-every-exit-path property is no longer a free consequence of there being only one exit path, and has to be *reconstructed*. In this machine it is reconstructed by =detail::k_protect=, a continuation frame that intercepts all three alternatives of =outcome= and funnels them through the same cleanup sequence before re-emitting whichever one it saved.

** The interned symbol table survives into the runtime program

Decision D12's symbol table (=smd::cl::symbol::symbol_table=, step R2) is not reader-only scaffolding that a later stage discards: the same table instance that interning built is the one the evaluator resolves every variable, function-slot, and =eq= comparison against at run time (=eval::symbol_table=, step R5's alias over it in =src/smd/cl/eval/builtin.hpp=). That is only safe because the table owns its name characters outright -- interning copies a name into the table's own pool rather than storing a view into the reader's datum arena or any other caller-owned storage -- so a program built from this table is self-contained the moment elaboration finishes, with nothing left dangling once the source text and the datum tree that read it go out of scope. This is the rebuild's answer to the dangling-view failure =docs/divergences/DIV-0007= documents for the pivot's =source_literal=: R2 designed the table so that failure mode has no equivalent here, not by patching it after the fact but by never storing a borrowed view in the first place.

** =core_cons=: a deliberate exception to "lower before you add a tag"

Decision D18 asks the elaborator to lower a new form onto existing =core_tag= alternatives before adding a new one. =core::core_cons= (step R4) is the one form R4 added anyway, and the reason is worth keeping on record rather than re-deriving: the obvious lowering for quoted list data, an ordinary call to the function named =CONS=, is not merely inelegant but *wrong*. ANSI quoted data is a literal, so =(quote (1 2))='s pairs must exist independent of what a program does to the function slot of =CONS= at run time -- a program that redefines =cons= must still get ordinary pairs from its quoted lists, and =core_call{CONS}= cannot express that independence. =core_cons= is a hermetic pair constructor with no dependency on any symbol's function slot, used only by =elaborator::emit_quoted_list= (quoted data) and never by an ordinary call to =cons= (which does lower onto the =CONS= builtin, in the function slot, exactly as D18 prefers). It is the one node kind in the rebuild's core AST that decision D18's own text names as its expected exception, not a quiet violation of the rule.

** The sender backend drives the machine; it does not fork it

Decision D17 asks for a second backend over =smd::cl='s core tree, using Beman Execution, and step R7 built =smd::cl::sender::machine_sender= to be it. Two shapes were on the table. One forks =eval::machine::evaluate_subforms='s frame, so a call's arguments run as sibling senders joined by =when_all= -- the pivot's trick (=smd::smdlisp::sender::sender_eval=), minus the pointer tree the pivot needed to see the independent set at all. The other treats one whole =machine::run= as the unit a sender completes: connect a sender, and =start= drives the machine's own trampoline to completion before dispatching its =eval::outcome= onto the matching completion function.

R7 chose the second, and the argument is a concrete cost rather than a preference. =eval::machine= is single-owner state -- one frame stack, one heap, one control register, mutated in place by =step= -- so forking an argument list means either splitting that state across concurrently-started senders, which nothing in the frame design supports, or recursing through a second evaluator built for the purpose, at which point R5's whole point (no evaluation recursion is C++ recursion, so depth and step count are diagnosed capacities rather than the C++ stack -- =limits::frames=, =limits::steps=) would be rebuilt on the sender side and immediately spent: =limits::steps= defaults to 200000, and chaining that many sender continuations recursively is 200000 C++ activation records.

#+transclude: [[file:../src/smd/cl/sender/machine_sender.hpp::0c10d654-ec97-4580-9c14-aed654701bbf]] :lines 2- :src cpp :end "0c10d654-ec97-4580-9c14-aed654701bbf end"

The channel mapping is D13's, spent a second time: a value to =set_value=, a diagnosed error to =set_error=, an unwind in flight to =set_stopped=. Execution26's stopped channel is niladic, so an unwind that reaches =machine::run= uncaught -- meaning every live =block=/=catch= inside the program already had first refusal at it, per =detail::k_block='s own resume logic -- completes with no payload; there is nothing left to carry a target and a value to, and nothing downstream that still needs them. =smd::cl::sender::run_sender= (the inverse direction, a completion turned back into an =eval::outcome= for a caller that wants one) reports that case as a diagnosed error, the same choice the pivot's =to_result= makes for an unwind that reaches the top of a program.

What this shape still buys, honestly: two whole-program evaluations are genuinely independent senders -- separate machines, separate heaps, no shared mutable state -- so joining them with =when_all= is a true structural-independence claim, never a claim about evaluation order inside either program. =machine_sender.test.cpp='s ~WhenAllJoinsTwoIndependentPrograms~ is that claim and nothing stronger; R7's step brief is explicit that ANSI's left-to-right argument order (3.1.2.1.2.3) is not up for renegotiation once an argument can have an effect, and nothing here reorders one.

DIV-0015 (accepted-permanent: Beman Execution's =connect=/=start=/=sync_wait= are not constant-evaluable) means none of this is =constexpr=, unlike =eval::machine= itself; that absence is stated in the type rather than discovered only in the tests, exactly as DIV-0015 asks of a future sender component. See =docs/divergences/DIV-0016-mendler-para-rederived-for-foundation-fix.md= (2026-08-15 note) for the fuller argument against the forking shape, including why the choice was not underdetermined between the two.

** The kit: a real second target with one real client

Step R8 extracts seventeen files into =smd::kit::foundation= (=src/smd/kit/foundation/=, target =kit.foundation=): the nine =docs/cl-rebuild-plan.md= §5 named as "essentially zero drift" -- =static_vector=, =result=, =parse_error=, =source_pos=, =source_span=, =arena_box=, =functor=, =applicative=, =alternative= -- plus =foldable=, =traversable=, =monoid=, =identity=, =fold_left_short=, =trampoline=, =result_instances= and =static_vector_instances=, which decision 2 excluded on first pass and a correction from the repository owner put back. What actually shipped is narrower than §5's sentence in one direction (§ decision 3, below) and was, for one commit, narrower than the corrected standard in another (decision 2). Both gaps are worth stating rather than papering over.

*Decision 1: what is the kit's version of a diverged file.* Diffing all three copies (=smdscheme=, =forth=, and R1's =cl= union) shows six files -- =source_pos=, =source_span=, =functor=, =applicative=, =alternative=, plus =arena_box= at a handful of lines -- unchanged in substance across all three; that is §5's zero-drift signal, verified rather than assumed. Three files carry real cl-side growth: =static_vector= gained =filled=, =append_range=, =pop_back=; =result= gained =value_type=, equality, and =and_then=; =parse_error='s equality became a merged best-of (scheme's same-pointer fast path, forth's explicit null check, cl's =std::string_view= comparison in place of a hand-rolled loop). Every one of these additions is generic over the datatype and carries no Lisp-specific type in its signature, so all three travel with the extraction as a strict superset rather than staying cl-only. D14 is unaffected: =static_vector='s =Capacity= is still its own template parameter in every one of the three old copies and the new one.

*Decision 2: where the kit's boundary is, and the standard that actually decides it.* =src/smd/cl/foundation/= originally held thirteen files the older two copies never had: =foldable=, =traversable=, =monoid=, =identity=, =node_f=, =topo_fold=, =trampoline=, =fold_left_short=, =result_instances=, =static_vector_instances=, =tagged_tree=, =tagged_tree_instances=, =tagged_tree_schemes=. §5 rules the AST-shaped ones out by name -- =node_f=, =topo_fold=, =tagged_tree*=, and by extension =tagged_tree_instances=, the adapter that gives =tagged_tree= its Foldable and Traversable instances -- and that part of the cut stands: those five name an AST type and belong with the AST, not the substrate.

The other eight -- =foldable=, =traversable=, =monoid=, =identity=, =fold_left_short=, =trampoline=, =result_instances=, =static_vector_instances= -- were first placed with the AST group on a different argument, which was wrong and is recorded here precisely because getting it wrong once is the durable lesson. The reasoning was: §5's stated test for kit membership is "generic in shape and free of language-specific types," but §5's own supporting *evidence* for the nine files that did extract cleanly was narrower than its stated test -- "two independent implementations converged with no semantic divergence" -- and neither =smdscheme= nor =compile-time-forth= had ever needed a Foldable, Traversable, Monoid, or Identity instance, so these files looked like a sample of one. That reasoning silently swapped the *test* (generic and language-agnostic) for a *proxy* (has a second implementation already been written), and the two came apart here: =compile-time-forth= has not had the algebraic refactoring done on it that =cl= has, because nobody has done that work yet, not because its `machine`/`interpreter` state has no shape a Foldable or a Traversable would fit. The absence of a second copy measured a sibling project's backlog, not this code's generality. Re-applying §5's actual test rather than the proxy: every one of these eight is generic in every type it names and free of anything from a parser, a reader, or an AST -- =foldable=/=traversable=/=monoid=/=identity= are the same CPO shape as =functor=/=applicative=/=alternative= applied to a different pair of typeclasses; =fold_left_short= and =trampoline= are algorithms over an abstract range and an abstract state machine respectively, motivated by decision D15 and by step R5's evaluator but naming neither; and =result_instances=/=static_vector_instances= adapt =result=/=static_vector= to Functor/Applicative/Foldable/Traversable, and once all four of those typeclasses and both of those datatypes live in the kit, an adapter between them is kit material by the same logic, not cl material that happens to reach into the kit. All eight move.

The lesson to keep is not "these particular eight belong in the kit" but which question to ask next time: whether a file is generic and language-agnostic is a property of the file, checkable directly. Whether a second implementation happens to exist yet is a property of some other project's schedule. The first is §5's real bar; the second was only ever meant to be corroborating evidence for it, and corroboration that has not arrived yet is not the same claim as a test that has been failed.

*Decision 3: the "third client" premise, corrected.* §5 says extraction happens "once Common Lisp is the third working client," of both =foundation/= and =parser/= (=cursor=, =parser=, =alt=, =parser_ops=). That premise holds for =foundation/='s files -- =src/smd/cl/foundation/= genuinely defines and uses all of them, so cl is a real, working, in-tree client, verified by grep across =reader=, =elaborator=, =eval=, =sender=, =symbol= and =conformance=. It does not hold for =parser/=: =src/smd/cl/reader/cursor.hpp= is a hand-written, differently-shaped type -- no =parser<F>= wrapper, no =alt= combinator, =parse_state= folded directly into the cursor rather than living beside a generic =parser= type -- and nowhere under =src/smd/cl/= defines or uses anything resembling =parser<T>=, =alt=, or =parser_ops=. R3 built a readtable-driven hand-rolled reader instead, and nothing in the plan or the divergence log records that as a deliberate rejection of the combinator style; it is simply the shape R3 chose. The practical consequence: even the diminished claim R8's brief anticipated -- "cl is at least *a* working client, even if =smdscheme= and =forth= can't be re-pointed at the kit in this repository" -- is false for =parser/= specifically. Cl is not a client of the parser combinator layer at all. §5's "third client" premise is therefore correct for =foundation/= and does not apply to =parser/=; R8 extracts the former and leaves the latter entirely alone, undiffed and unmoved, pending either a =cl= reader rewritten onto combinators or a fourth real front end that needs them. See the dated correction appended to §5 of =docs/cl-rebuild-plan.md= for the fuller argument and see =docs/divergences/DIV-0028-parser-combinator-layer-has-no-cl-client.md= for the classification.

*The mechanism: a shim, not a rename.* =smd::cl::foundation='s namespace is preserved even though these seventeen files' definitions moved, because every consumer under =src/smd/cl= reaches =foundation::X= by unqualified name relying on ordinary nested-namespace lookup (=smd::cl::foundation= is a sibling of =smd::cl::reader=, =smd::cl::eval=, etc., found by searching enclosing namespaces) -- renaming the namespace to =smd::kit= would have silently broken every one of those call sites. Instead, =src/smd/cl/foundation/result.hpp= (and its sixteen siblings) become forwarding shims: same include path, same guard, same namespace, each with a =using= for exactly the names the original header exported, now naming =smd::kit::foundation='s definitions.

No file outside =src/smd/cl/foundation/= changed to make this true -- not =reader=, =elaborator=, =eval=, =sender=, =symbol=, nor =conformance=, nor =core= -- because both of the two things a caller could depend on (the include path and the qualified name) are unchanged. Moving =result_instances.hpp= and =static_vector_instances.hpp= wholesale, rather than leaving them in cl with a namespace-reopening workaround the way the first cut did, dissolves an awkwardness rather than papering over it: once =result=/=static_vector= and their Functor/Applicative/Foldable/Traversable typeclasses are all in the same namespace, the instance's own specializations are ordinary same-namespace code again. =tagged_tree_instances.hpp= is the file that still needs the workaround, honestly, because it is the genuine case the workaround exists for: =tagged_tree= stays in cl (AST machinery, decision 2), but all three typeclasses it instantiates are now kit-owned, so all three of its specializations -- Functor, Foldable, and Traversable alike -- open =namespace smd::kit::foundation= explicitly and name =smd::cl::foundation::tagged_tree= by qualification.

The honest scope of "extract the kit" in this repository, stated plainly: one real client (=smd::cl=), not three. =smdscheme= cannot be repointed at the kit without violating the "never edit =smdscheme= in place" rule (=AGENTS.md=), and =compile-time-forth= is a separate repository this project can read but not modify. What R8 delivers is a kit-shaped tree with a working build target, a real client, and the three-way diff as evidence that the other two copies could adopt it unchanged if their own maintainers chose to -- not an actual three-tenant migration, which no single step in this repository could perform.
