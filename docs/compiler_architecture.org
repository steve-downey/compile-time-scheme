* Introduction

This document details the compile-time compiler architecture for SchemePoC, a Scheme-light compiler proof-of-concept targeting C++26. Phases 1 through 7 below are drawn from the frozen reference tree =src/smd/smdscheme/= (see decision record D1). The Common Lisp layer =src/smd/smdlisp/= reuses this same staged architecture with a different front end and environment model, and is consolidated into this document in "The Common Lisp Layer", below.

For many C++ developers, compiler jargon and functional programming idioms can feel like a completely different language. This document translates those concepts into familiar C++ terms. We are building a compiler entirely inside C++ standard constant expressions (`constexpr`).

Rather than parsing strings directly into executable code in one messy step, this compiler uses a *staged pipeline*. It breaks the problem into distinct transforming phases:

1. **Reader**: Strings -> Reader Datum Tree
2. **Elaborator**: Reader Datum Tree -> Core Semantic Tree
3. **CPS IR**: Core Semantic Tree -> Continuation-Passing Style Intermediate Representation
4. **Backend**: CPS IR -> Executable C++ Objects (Closures or Sender Graphs)

* Phase 1: Applicative Parser Combinators

Parsing text manually with "recursive descent" (writing a massive tree of `if/else` and `while` loops to eat characters) is error-prone. Instead, we use **parser combinators**. Think of combinators as small, composable C++ objects. You build a parser for a complex grammar by snapping together smaller parsers (e.g., "parse a digit", "parse a letter") using operations like "and then", "or", and "many".

In C++26 `constexpr` contexts, we run into a limitation: you cannot easily juggle C++ lambdas that capture variables and convert them into function pointers. To solve this, our "applicative" library represents parsers as literal C++ callable objects (functors with `operator()`).

* Phase 2: Reader Datum Tree (Understanding "Atoms")

In languages like C++, the text you type is directly representing instructions. In Lisp and Scheme, the text you type represents **data structures** (lists). This concept is called "homoiconicity", and it's why Lisp has so many parentheses.

The Reader's only job is to turn text into lists and **atoms**. In this context, an **atom** is simply any fundamental piece of data that isn't a list. The number `42` is an atom. The boolean `#t` (true) is an atom. The symbol `foo` is an atom.

At this stage, the compiler doesn't know if the list `(+ 1 2)` is a mathematical operation or just a literal list of three items. It merely builds the tree of atoms and lists. Because standard heap-allocated trees (using `new` or `std::vector`) cannot easily survive across the C++26 compile-to-runtime boundary, we construct this tree in a "flat arena"—a fixed-size array where nodes refer to each other by integer indexes (`node_id`).

* Phase 3: Elaboration and Core Semantic IR

**Elaboration** is compiler jargon for "figuring out what the code actually means."

Once we have a tree of lists and atoms, the Elaborator walks that tree and assigns C++ semantic types to it. If it sees a list starting with the symbol `if`—like `(if #t 1 2)`—it "elaborates" that into a `core_if` structure representing a conditional branch. If it sees a regular list like `(+ 1 2)`, it elaborates it into a `core_application` (a function call).

Elaboration is where syntax errors are caught natively before we ever try to execute them. By keeping reading (Phase 2) and elaboration (Phase 3) separate, the code remains much simpler.

* Phase 4: CPS vs. Direct Evaluation (`eval_direct`)

There are two primary ways to evaluate an abstract syntax tree:

**1. Direct Evaluation (`eval_direct`)**:
This is the simple interpreter approach. You write a C++ function that takes a tree node, figures out what to do, computes the result, and `return`s it. If a node has children (e.g. arguments to a function), `eval_direct` calls itself recursively. The downside? Deeply nested programs will blow up the C++ call stack. Also, supporting advanced control flow (like early returns or tail-call optimization) is difficult when you're chained to standard C++ `return` semantics.

**2. Continuation-Passing Style (CPS)**:
CPS is an alternative plumbing method for programs. Instead of a function *returning* a value, every function takes an extra argument: a callback representing "what to do next with the result." This callback is called the **continuation**.

If you want to compute `(A + B) * C` in CPS:
1. Compute `A`, pass it to a continuation.
2. In that continuation, compute `B`.
3. Pass `A` and `B` to the `+` function, along with a continuation for `*`.
4. In that continuation, take the sum, evaluate `C`, and pass them to the `*` function...

Why do this? Because if you never standardly `return`, but instead always call "what happens next", you explicitly expose the control flow. Tail calls just become regular function calls that don't add to the stack. Furthermore, this maps *perfectly* to asynchronous programming in modern C++. A "continuation" in compiler jargon is exactly the same concept as a `.then()` or a `receiver` in C++ async execution (like Beman senders).

* Phase 5: Closure Backend Materialization

For C++ developers, it may seem confusing that a language can be executed using *only* Closures and CPS.

A **Closure** is essentially a `struct` containing a function pointer (or `operator()`) alongside the local variables it captured from its surrounding scope (like a capturing C++ lambda).
If you combine:
- **Closures** (to preserve state and context).
- **CPS** (to handle branching, looping, and returning by calling a "what happens next" callback).

You have all the ingredients necessary for a Turing-complete runtime. You don't need a virtual machine with a stack pointer and assembly instructions.

This Backend phase takes our CPS representation and translates it into completely standard, strongly-typed C++ closure objects. We don't use heavy type-erased wrappers like `std::move_only_function` or `std::any` because they introduce overhead (virtual calls, dynamic allocation). Instead, we emit exact, statically-known template wrappers.

Because we used CPS, this phase is structurally identical to building a C++26 sender graph (`sync_wait(when_all(...))`), preparing the compiler natively for future async integration.

* Phase 6: Sender Backend and Asynchronous Execution

Once the execution has been mapped out in Continuation-Passing Style (CPS) using standard C++ Closures, it becomes remarkably straightforward to adapt to standard C++ Asynchronous Execution.

In traditional C++ asynchronous environments (like `std::execution` from C++26 / Beman `sender/receiver` models), an operation doesn't immediately return a result; it *sends* its result to a *receiver*. Look closely: a "receiver" is conceptually identical to a "continuation" in CPS.

The Sender Backend walks our Core Semantic AST exactly like the Closure backend does, but instead of constructing plain callable functors, it builds a robust graph of asynchronous `sender` objects (utilizing components like `beman::task::task`). Variables captured in the environment are awaited asynchronously when function applications occur. This architecture guarantees that Scheme programs can invoke C++ co-routines seamlessly, and it leverages the target machine's thread pools for transparent concurrency underneath the simple Scheme code.

** A sender has three completion channels, and that is a semantic resource

A durable consequence, recorded here because it outlives the step that found it and applies to any backend built on senders, not only to the Common Lisp one.

A receiver is conceptually a continuation, as above -- but it is *three* continuations, not one. `set_value`, `set_error` and `set_stopped` are three separate functions, and an interpreter can spend that structure rather than merely carry it.

The Scheme backends above never do. They return a single `result<value>`, so a value and a diagnosed error share one wire and are told apart by inspecting the payload. That is fine while a language has only two outcomes. It stops being fine as soon as the language grows non-local control: with `block`/`return-from` and `catch`/`throw`, *four* things travel that one wire -- a value, an error, and two kinds of unwind -- and telling them apart needs an out-of-band discriminator. In the closure backends that discriminator is a pair of sentinel `parse_error` messages compared by pointer identity, which in turn forces them to be named `inline constexpr char[]` objects rather than bare string literals, because equal string literals may not share an address.

Mapping the same language onto senders deletes that machinery instead of porting it. A value goes to `set_value`, a diagnosed error to `set_error`, an unwind in flight to `set_stopped`; nothing is multiplexed, so nothing needs discriminating, and the sentinels have no work left to do. The question a `block` still has to answer -- "is this unwind aimed at *me*?" -- is answered where it always was, by a flag on its own exit record.

The second consequence is where cleanup lives. Under direct or CPS evaluation, "run the cleanup on every exit path" is achieved by arranging that there is only one exit path: the four outcomes are already merged into one value before `unwind-protect` sees them, so a single unconditional statement suffices. A sender backend cannot inherit that from C++ control flow, because the three channels really are three functions called from three places. The property has to be *reconstructed*, and the natural place to reconstruct it is a receiver whose three completion functions all funnel into one -- which makes `unwind-protect` an ordinary sender adapter rather than an evaluator special case, and makes "cleanup runs on all three channels" a structural property rather than a checklist.

The reverse direction is worth stating too, since it is the part that does not carry over: the restore step for a *dynamic binding* stays in ordinary C++ control flow around the recursive call, because it brackets a callee's whole extent rather than a single sender's completion. A sender backend is not uniformly better; it is better exactly where the thing being expressed is a completion.

* Phase 7: Data Reification with C++26 Reflection (`std::meta::info`)

In an ordinary compiler targeting C++, data environments and captured scopes are rigidly defined structures (`struct { int a; char b; };`). To mimic dynamic scope capturing (like an environment map dictating variables available to a Scheme Lambda), one might traditionally reach into `std::map<std::string, std::any>`. But that implies heap allocations at runtime, virtual dispatch, and cache misses.

C++26 introduces **Reflection**: the ability to interact with types as first-class `constexpr` values (`std::meta::info`).

We use this feature in the Reification phase to take the environment layouts calculated entirely inside our compile-time ast `constexpr` code, and command the compiler to dynamically generate hard-coded `struct` representations that match exactly. Using `std::meta::define_aggregate`, we essentially instruct the C++ compiler: "I analyzed this Scheme function. It expects two integers and a boolean. Generate a bespoke C++ `struct` to perfectly fit this requirement, and let's map it across."

This results in environment sizes that are as zero-cost as though a C++ expert manually wrote a distinct structure for every single lambda parameter capture.

* The Common Lisp Layer: =smd::smdlisp=

Everything above builds a small Scheme. =smd::smdlisp= is a second front end over the *same* staged pipeline -- reader, elaborator, CPS, backend -- built for a subset of ANSI Common Lisp instead of Scheme. It is not a fork of the pipeline; it is a second package that reuses the pipeline's shape while trading Scheme's single namespace for a Lisp-2 (separate value and function namespaces), lexical scoping's simplicity for `defvar`/`defparameter` special variables and dynamic (shallow) binding, and Scheme's small control-flow surface for `block`/`return-from`, `catch`/`throw`/`unwind-protect`, `tagbody`/`go`, and `multiple-value-bind`. Every one of these forms compiles through all three backends described in Phases 4 through 6 above -- a direct tree-walking evaluator, a CPS-compiled closure backend, and a Beman-Execution sender backend -- with one gap, noted below.

For everything this section states as fact but does not re-derive, see [[file:cl-limitations.md][=docs/cl-limitations.md=]], the consolidated record of every ANSI divergence this layer makes.

** From datum to core: two new special forms

The elaborator (Phase 3, above) grows two new alternatives in its core AST to carry Common-Lisp-specific control flow that has no Scheme counterpart: multiple-value binding, and `tagbody`/`go`.

`multiple-value-bind` is a *binding* form, not a function call, so it cannot be lowered the way `values` is (next section). It elaborates to a real `core_lambda` over the bound variable names, which the evaluators *call* -- the same "lower a binding form to a lambda application" strategy already used for `let`. That is what lets it inherit implicit progn, arity checking, closure capture, and the special-variable dynamic-binding rule for free.

#+transclude: [[file:../src/smd/smdlisp/elaborator/elaborated_core.hpp::98a22b58-964f-4853-be88-20a1d4a9b9d6]] :lines 2- :src cpp :end "98a22b58-964f-4853-be88-20a1d4a9b9d6 end"

`tagbody` is where the elaborator does real work rather than a simple translation: the source body is a single sequence interleaving ordinary statements with bare tags (symbols or integers), and ANSI CL requires a forward `go` to a tag stated later in the same body to work. The elaborator therefore makes two passes over the body -- once to collect every tag's position, once to elaborate the statements with all tags already in scope -- so that by the time either evaluator sees a `core_tagbody`, the interleaved source is already split into an ordered statement vector and a tag-to-index table. No evaluator re-derives the basic blocks.

#+transclude: [[file:../src/smd/smdlisp/elaborator/elaborated_core.hpp::8e268a26-7eaa-470f-86e5-3597d376b700]] :lines 2- :src cpp :end "8e268a26-7eaa-470f-86e5-3597d376b700 end"

There is deliberately **no** `core_values` node beside `core_multiple_value_bind`. In ANSI CL, `values` is an ordinary *function*, not a special operator, so `(values 1 2)` elaborates to a plain function call and needs no elaborator support of its own; see the next section for where that pays off.

** The value channel widens: multiple values

Scheme's evaluators (Phase 4) return one value per form. Common Lisp's evaluation relation does not: a form produces a possibly-empty *sequence* of values, of which a single-value context (an `if` condition, a function argument) takes only the first. Rather than hang a side "values register" off the environment -- which would make "who last wrote the register" a global invariant every arm of every backend has to maintain by hand -- the closure backends widen their *return channel* itself to a small fixed-capacity vector.

#+transclude: [[file:../src/smd/smdlisp/closure/value.hpp::a4a90af9-fd64-4f75-ad47-609c7c1e50fd]] :lines 2- :src cpp :end "a4a90af9-fd64-4f75-ad47-609c7c1e50fd end"

Because that widening happens in the return channel, multiple values propagate correctly out of every tail position that already had to produce a result -- an `if` branch, a `progn`'s last form, a lambda body's last form -- with no extra machinery. They do *not* propagate through a nonlocal exit: `return-from` and `throw` still carry a single value, because their payloads live in a `block`/`catch` activation record, not in the return channel (=docs/cl-limitations.md=, DIV-0019). That is the honest one-line summary worth carrying forward: multiple values propagate through returns, not through escapes.

** Closure backend: environment, dynamic binding, and nonlocal exit

`smd::smdlisp::closure::env` is a Lisp-2 environment: two independent binding lists (value namespace, function namespace), plus a third for `block`/`return-from` exit records and a fourth for `tagbody`/`go` tags. All four are appended to the *ambient* environment a body shares, which is what lets a `setq` or `defun` anywhere in a sequence of statements mutate the one environment every sibling statement sees -- and is also the direct cause of the shadowing divergence described in =docs/cl-limitations.md= (DIV-0021).

Special variables use *shallow* dynamic binding: a special has exactly one value cell, and binding it saves the old contents, overwrites the cell, and restores the saved contents when the binding's extent ends. Every environment that names the variable -- including a closure captured long before the binding -- resolves to that same cell, which is the entire mechanism and the entire reason `setq` of a special needs no special case.

#+transclude: [[file:../src/smd/smdlisp/closure/eval_direct.hpp::e0468b60-4a31-4526-bd12-722bbd15ceac]] :lines 2- :src cpp :end "e0468b60-4a31-4526-bd12-722bbd15ceac end"

Nonlocal exit reuses the same identity-compared-sentinel technique the Scheme backends use for propagating an out-of-band signal through a frozen two-alternative result type, extended from one marker to three: `return-from` (step L14) and `throw` (step L15) each already needed their own distinct marker, and step L23 (`tagbody`/`go`) adds a third rather than reusing either of the first two, because a `block`, a `catch`, and a `tagbody` must each let the *other two* kinds of transfer pass through untouched.

#+transclude: [[file:../src/smd/smdlisp/closure/env.hpp::1232b7f6-c9b9-4611-a958-bd1bb14b0ff5]] :lines 2- :src cpp :end "1232b7f6-c9b9-4611-a958-bd1bb14b0ff5 end"

`go` reuses the same `exit_record` type `block` uses, rather than inventing a parallel record type, because a `tagbody` activation needs exactly the same two things a `block` activation needs: a stable, arena-allocated identity a closure can capture, and a `live` flag saying whether the activation is still running. The one reinterpretation is the payload, which for a `tagbody` is the index of the basic block to resume at rather than a value being returned.

#+transclude: [[file:../src/smd/smdlisp/closure/env.hpp::222e7d9c-2121-4831-bd34-b4110a310577]] :lines 2- :src cpp :end "222e7d9c-2121-4831-bd34-b4110a310577 end"

The direct evaluator's `tagbody` handling is a small trampoline over the basic blocks the elaborator already laid out: a program counter walks the statement vector, an ordinary result advances it, and a `go` aimed at this activation resets it and marks the activation live again -- which is what makes `tagbody` iterate rather than merely escape.

** CPS backend: the tagbody trampoline is deliberate, not incidental

The CPS backend (Phase 4) ordinarily expresses control flow by having each node's continuation be *another* continuation object -- no C++ return, no C++ stack growth, tail calls that stay tail calls. `tagbody`/`go` is the one place that pattern is deliberately broken: a `go` that tail-called its target block as a continuation would grow one C++ frame per loop iteration, so a compile-time loop meant to demonstrate iteration without recursion would instead exhaust the constexpr evaluation depth. The fix is to trampoline the transfer through the one frame that owns the `tagbody`, exactly as the direct evaluator does, rather than expressing the loop as mutual tail calls between block continuations.

#+transclude: [[file:../src/smd/smdlisp/closure/cps_code.hpp::7d388d02-7ba7-45ab-84cd-38b213b37ab2]] :lines 2- :src cpp :end "7d388d02-7ba7-45ab-84cd-38b213b37ab2 end"

The demonstration this backend (and the direct evaluator, and =smdlisp.hpp='s public API, below) is built to run is iteration expressed with no self-recursion at all -- recall that recursive `defun` is unsupported (=docs/cl-limitations.md=, DIV-0009), so `tagbody`/`go` is the only iteration primitive this project has:

#+begin_src lisp
(let ((n 0)) (tagbody top (setq n (+ n 1)) (if (eql n 3) nil (go top))) n)  ; => 3
#+end_src

This is `static_assert`-green in both closure backends and in =smdlisp.hpp='s public `compiled_lisp`, and runtime-green in the sender backend below, which has no constexpr twin at all -- for reasons the next section states precisely rather than assumes.

** Sender backend: the same three channels, spent on a second language

Phase 6, above, records a durable fact that outlives any one language: a sender's three completion channels (`set_value`, `set_error`, `set_stopped`) are a semantic resource, not just a wider vocabulary for "return". The Common Lisp sender backend is where that resource gets spent a second time, on a language with four things -- a value, a diagnosed error, and two kinds of unwind -- that the closure backends have to multiplex onto one two-alternative result.

#+transclude: [[file:../src/smd/smdlisp/sender/outcome.hpp::5c044086-ef0c-4041-8f39-b89b92cde079]] :lines 2- :src cpp :end "5c044086-ef0c-4041-8f39-b89b92cde079 end"

Observing a program's completion is deliberately not `sync_wait`, because `sync_wait` collapses two of the three channels back together (an engaged optional for a value, a disengaged one for stopped, and a **throw** on an error) -- exactly the multiplexing this backend exists to avoid. `connect` plus `start` with a small recording receiver is the honest primitive instead.

#+transclude: [[file:../src/smd/smdlisp/sender/outcome.hpp::6ffe3840-6f72-435d-b975-b945cd4e46f2]] :lines 2- :src cpp :end "6ffe3840-6f72-435d-b975-b945cd4e46f2 end"

Which channel a `smdlisp` form completes on is not known until the form has been evaluated, and none of the stock sender factories can express "decide at start time" -- `just` always completes with a value, `just_error` always with an error. The backend's one leaf sender exists to fill exactly that gap, and its laziness is load-bearing: nothing inside it runs until the operation state is started, which is what lets `unwind-protect` (next) genuinely place the protected form's evaluation *inside* its own operation.

#+transclude: [[file:../src/smd/smdlisp/sender/defer_outcome.hpp::e64f025f-7464-419a-b739-301569245544]] :lines 2- :src cpp :end "e64f025f-7464-419a-b739-301569245544 end"

`unwind-protect` is where the payoff of three real channels is clearest. The closure backends get "run cleanup on every exit path" by arranging that there is only one exit path -- a value, an error, and both kinds of unwind are already merged into one result before `core_unwind_protect` ever sees them, so a single unconditional statement suffices. A sender backend cannot inherit that from C++ control flow, because the three channels really are three functions, called from three different places inside the child operation; the property has to be *reconstructed*. It is reconstructed by a receiver whose three completion functions all funnel into one `finish`, which is what turns `unwind-protect` into an ordinary sender adapter instead of an evaluator special case.

#+transclude: [[file:../src/smd/smdlisp/sender/unwind_protect.hpp::cae50b27-0d34-4779-b73f-7d625d1060d8]] :lines 2- :src cpp :end "cae50b27-0d34-4779-b73f-7d625d1060d8 end"

The evaluation algebra itself is a Mendler-style paramorphism over the core AST -- structurally the same recursion scheme `smd::fixpoint` already provides, but re-derived locally rather than reused, because the `smdlisp` core AST's fixed-point type is nominally distinct from the one the shared library expects, and the frozen Scheme tree cannot be given a conversion between them (=docs/cl-limitations.md='s "Known internal duplications", DIV-0016).

#+transclude: [[file:../src/smd/smdlisp/sender/sender_eval.hpp::59265482-a0f4-4b96-9820-89abdc54f268]] :lines 2- :src cpp :end "59265482-a0f4-4b96-9820-89abdc54f268 end"

`cons` is the one node in the whole algebra whose two children are structurally independent of each other, and so the one place a real `when_all` join -- rather than an ordinary sequence -- says something true about the program being evaluated.

#+transclude: [[file:../src/smd/smdlisp/sender/sender_eval.hpp::44233d7a-ff4b-4c3d-b5ff-006c7ee0fd1d]] :lines 2- :src cpp :end "44233d7a-ff4b-4c3d-b5ff-006c7ee0fd1d end"

`block`/`return-from` and `catch`/`throw` are where the three-channel design earns its keep most visibly: an in-flight unwind completes on `set_stopped` with no payload at all, because the payload already lives in the targeted exit or catch record, and "is this transfer aimed at me?" is answered the same way it is in the closure backends -- by testing `live` on that record.

#+transclude: [[file:../src/smd/smdlisp/sender/sender_eval.hpp::02f32bd6-6a27-4b63-b0b8-744347bc6484]] :lines 2- :src cpp :end "02f32bd6-6a27-4b63-b0b8-744347bc6484 end"

`unwind-protect` itself is the one form in this algebra that is not evaluated directly at all: it is delegated whole to the sender adapter above, with the protected form wrapped as a lazy child sender and the cleanup forms wrapped as the adapter's cleanup thunk.

#+transclude: [[file:../src/smd/smdlisp/sender/sender_eval.hpp::06514953-0711-4ac8-b392-9fad1aed130e]] :lines 2- :src cpp :end "06514953-0711-4ac8-b392-9fad1aed130e end"

`tagbody`/`go` needed no new machinery at all to reach the sender backend, which is worth stating plainly next to the paragraph that follows it: a `go` is a nonlocal transfer, `set_stopped` already *is* that channel, and `live` alone still answers "aimed at me?". This is a transcription of the closure backends' trampoline (above), with the identity-marker comparison simply deleted, because an unwind and an ordinary error can no longer be confused on this backend.

What did *not* make it across is `multiple-value-bind` and `values`: as of this section, they are the only two forms where the three backends disagree on the object language (=docs/cl-limitations.md=, DIV-0017/DIV-0018). Also worth restating precisely, because it is easy to over-claim by analogy with the closure backends above: **this backend has no `static_assert` twin for any of it.** Beman Execution's `connect`/`start` is not constant-evaluable, so a sender graph cannot produce a compile-time value, so there is nothing for a `static_assert` to assert against. Every one of the transcluded arms above is exercised only by a runtime `TEST_CASE`. Do not describe all three `smdlisp` backends as compile-time evaluators; only the direct evaluator and the CPS closure backend are.

** Limitations

This section states what the Common Lisp layer *is*; it deliberately does not restate everything it is not. [[file:cl-limitations.md][=docs/cl-limitations.md=]] is the single consolidated record of every ANSI Common Lisp divergence across the reader, the evaluation model, control flow, macros, multiple values, the sender backend, and build/constexpr limits -- consult it rather than this section for the full, itemized list.

* The Common Lisp Rebuild: =smd::cl=

=smd::smdlisp= above is the pivot; =smd::cl= (=docs/cl-rebuild-plan.md=) is the rebuild that supersedes it, one pipeline stage at a time, from step R1 onward. This section records only the facts steps R2, R4 and R5 asked to have carried here -- it is not a restatement of the rebuild's plan or of =docs/divergences/=, which classifies every deliberate gap the rebuild has accepted so far.

** The evaluator is a machine, not a fold

=smd::cl::eval::machine= (step R5) evaluates the elaborator's core tree with a small-step abstract machine rather than a recursive walk. The reason is structural, not stylistic: the elaborator's three passes (Phase 3-equivalent for this tree, =docs/cl-pivot-plan.md='s D15) are folds over node indices because a fold visits every node in a fixed order, and evaluation cannot be made into one -- it visits an =if='s arms selectively, a function body once per call rather than once per node, and, past an unwind, not at all. What evaluation *is* instead is continuation-passing style with the continuations defunctionalised: a handful of =detail::k_*= frame types are the continuation constructors, a fixed-capacity frame stack is the continuation, and =machine::step= is the transition function, driven by one =foundation::trampoline= loop rather than C++ recursion.

#+transclude: [[file:../src/smd/cl/eval/machine.hpp::0b7a5e42-9d3c-4b19-83f4-6e5c2a1b7d04]] :lines 2- :src cpp :end "0b7a5e42-9d3c-4b19-83f4-6e5c2a1b7d04 end"

A consequence worth stating plainly: no evaluation recursion is C++ recursion, so the depth a program may reach is a diagnosed capacity (=limits::frames=) rather than the C++ stack, at compile time as at run time -- the same discipline =limits::steps= already applies to the step count as a whole.

** D13's three channels are now a type, not a discriminator convention

Phase 6's "a sender has three completion channels" observation, above, is what decision D13 generalises to an ordinary evaluator: =smd::cl::eval::outcome= carries a value, a diagnosed =foundation::parse_error=, or an =unwind= in flight as three distinct alternatives of one type, the same way a receiver's =set_value=/=set_error=/=set_stopped= are three distinct functions.

#+transclude: [[file:../src/smd/cl/eval/outcome.hpp::8f5b0a1c-3f0e-4f6f-95b0-2a0b4a5f6c31]] :lines 2- :src cpp :end "8f5b0a1c-3f0e-4f6f-95b0-2a0b4a5f6c31 end"

This is a sharper split than the pivot's closure backends ever had (=smd::smdlisp::closure=, above): those multiplex all four of their outcomes onto one two-alternative =result= and tell the cases apart with a pair of sentinel =parse_error= messages compared by pointer identity, which is why those sentinels had to be named =inline constexpr char[]= objects rather than bare literals. None of that machinery is ported. There is nothing left to discriminate, because there is nothing left multiplexed.

The consequence Phase 6 already named for senders applies here in exactly the same shape: splitting the channels means =unwind-protect='s run-the-cleanup-on-every-exit-path property is no longer a free consequence of there being only one exit path, and has to be *reconstructed*. In this machine it is reconstructed by =detail::k_protect=, a continuation frame that intercepts all three alternatives of =outcome= and funnels them through the same cleanup sequence before re-emitting whichever one it saved.

** The interned symbol table survives into the runtime program

Decision D12's symbol table (=smd::cl::symbol::symbol_table=, step R2) is not reader-only scaffolding that a later stage discards: the same table instance that interning built is the one the evaluator resolves every variable, function-slot, and =eq= comparison against at run time (=eval::symbol_table=, step R5's alias over it in =src/smd/cl/eval/builtin.hpp=). That is only safe because the table owns its name characters outright -- interning copies a name into the table's own pool rather than storing a view into the reader's datum arena or any other caller-owned storage -- so a program built from this table is self-contained the moment elaboration finishes, with nothing left dangling once the source text and the datum tree that read it go out of scope. This is the rebuild's answer to the dangling-view failure =docs/divergences/DIV-0007= documents for the pivot's =source_literal=: R2 designed the table so that failure mode has no equivalent here, not by patching it after the fact but by never storing a borrowed view in the first place.

** =core_cons=: a deliberate exception to "lower before you add a tag"

Decision D18 asks the elaborator to lower a new form onto existing =core_tag= alternatives before adding a new one. =core::core_cons= (step R4) is the one form R4 added anyway, and the reason is worth keeping on record rather than re-deriving: the obvious lowering for quoted list data, an ordinary call to the function named =CONS=, is not merely inelegant but *wrong*. ANSI quoted data is a literal, so =(quote (1 2))='s pairs must exist independent of what a program does to the function slot of =CONS= at run time -- a program that redefines =cons= must still get ordinary pairs from its quoted lists, and =core_call{CONS}= cannot express that independence. =core_cons= is a hermetic pair constructor with no dependency on any symbol's function slot, used only by =elaborator::emit_quoted_list= (quoted data) and never by an ordinary call to =cons= (which does lower onto the =CONS= builtin, in the function slot, exactly as D18 prefers). It is the one node kind in the rebuild's core AST that decision D18's own text names as its expected exception, not a quiet violation of the rule.
