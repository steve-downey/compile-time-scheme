# Blog transclusion pins

Generated by step B0 of `docs/epistolary-pinning-plan.md` on 2026-07-25.

Each post in the series that transcludes live code is pinned to one annotated
tag. `#+transclude:` links in a post resolve against that tag's tree, not
against the worktree, so a later refactor cannot rewrite the code inside an
already-published entry. `docs/compiler_architecture.org` is a living document
and deliberately keeps worktree resolution — it is *supposed* to roll forward.

Ten of the nineteen posts transclude no code and take no pin.

## Two authorship eras

P4 method 1 — first-parent walk of `main` for the merge carrying the step
identifier — works only for the Common Lisp pivot posts (16 onward). Those were
drafted on their step's branch and landed with a `--no-ff` merge, so the merge
commit is exactly "the revision the prose was written against."

From phase 20 on, the orchestrator creates the tag at the `--no-ff` merge and
the post is written against it, so there is no method to apply retroactively:
the pin is chosen before the prose exists. Phase 20 is a transitional case —
step L19 branched before `d0ff8ec` made pinning mandatory, so the post arrived
with worktree-path `orgit:` links and was repointed to `blog/phase-20`
immediately after the merge that the tag names. Regenerating it before and after
the repin produced byte-identical transcluded code, so the repin is
content-moot, exactly as the era-1 pin choices were.

Posts 5–12 predate that workflow. They are *retrospective*: the Scheme pipeline
was built first, and the blog was written afterwards about code that already
existed (`804edad`, the initial blog import; `e224146 docs: convert blog series
to org-mode with orgit transclusion`; `f56bdc8 docs(blog): fact-check fixes,
citation corrections, transclusion plumbing`). There is no per-phase merge to
find. For
these the pin is the last commit that modified the post's `.org`, which in every
case is also the commit that generated the committed `.md`. That choice makes
the pinned `.org` reproduce the published `.md`, which is the property that
matters: it isolates the leak from unrelated churn.

P4 method 2 (post date) was **not** used, and must not be used for this series.
Eleven of posts 0–13 carry `#+DATE: 2026-06-19`, a backfill date from the batch
that created them, and three carry dates earlier than commits they describe
(`phase-9`, `phase-12`: `2026-05-29`; `phase-11`: `2026-06-01`). Only posts
14–18 have dates written the day the step landed.

Within every post, the alternative candidate revision (step merge vs. the
DIV-0004 repoint commit for era 2; fact-check vs. voice-pass commit for era 1)
yields **byte-identical** transcluded regions. The pin choice is therefore
content-moot in all nine cases, and the table above picks the principled
commit rather than a merely convenient one.

## The measured leak

The leak was latent, not published: each `.md` was generated at the same commit
as its `.org`, so committed output is historically correct. Running `make
blog-md` today, before pinning, would have injected later code into three
earlier posts:

| Post | Anchor | Drift |
|---|---|---|
| `phase-18` | `cps_code.hpp` `180a37f4` | **+56 lines** — step L14's `block`/`return-from` code appearing inside the post about `setq`/`defun`/`progn` |
| `phase-5` | `comp_tree.hpp` `731f3ab0` | **+22 lines** |
| `phase-5` | `comp_tree.hpp` `950ee4f0` | **+2 lines** |
| `phase-17` | `eval_direct.hpp` `1d30e953` | **+1 line** |

Pinning therefore *prevents* a leak here rather than repairing a published one.
The regenerated `.md` for these posts should be unchanged from what is committed
— that is the check that pinning worked.

## Recorded discrepancy: duplicate UUID in `cps_code.hpp`

`phase-12-cps.org` transcludes `ceecf448-bff3-4b76-99cc-8c11ac4140f3` from
`src/smd/smdscheme/closure/cps_code.hpp`, where that UUID appears **three**
times, not twice, at every revision including `HEAD`:

- line 83 — opening anchor, before `cps_dispatch`'s signature
- line 100 — a second, stray opening anchor inside the `core_integer` lambda
- line 105 — the `... end` marker

The region still resolves: org's search option finds the first anchor and
`:end` stops at the end marker, so the transcluded block runs from line 83 to
line 104 and includes the stray comment on line 100 as a literal line of the
published code block. This is visible in the committed
`phase-12-cps.md` today and is not introduced by pinning.

Left as-is. `CLAUDE.md` forbids deleting or nesting existing UUID anchor pairs,
and this plan touches no source. The strict "UUID appears exactly twice" form of
the anchor test is therefore relaxed to "the region resolves" — a count other
than two is reported as a discrepancy, not a failure. Once phase 12 is pinned,
cleaning up that stray anchor becomes safe: it can no longer retroactively
alter the published post.

## Two pre-existing defects surfaced by the baseline

Neither is caused by pinning; both were found by regenerating the whole series
to measure the leak.

1. **Corrupt bibliography entry.** Commit `056e7e1 Update references.bib`
   replaced the author of `niebler2020p2300` with a literal placeholder,
   `author = {FIXME, WG21.bib}`. Regenerating today publishes
   `(FIXME, WG21.bib, 2024)` into `phase-8`, `phase-13`, and `phase-15`, which
   the committed `.md` files predate. Restored to `Dominiak, Michał and others`
   in a separate commit, so that step B4's diff is the measured leak and
   nothing else.
2. **Non-deterministic export ids.** `org-export` mints random `#orgXXXXXXX`
   anchor ids on every run, so every regenerated `.md` differs from the
   committed one by at least its ids, and `index.md` differs by ~100 lines of
   pure id churn. Pinning cannot make `make blog-md` byte-reproducible while
   this holds, so section 5 of the plan overstates "determinism": pinning makes
   the *transcluded code* reproducible, not the whole file. Fixing the ids
   (`CUSTOM_ID` properties, or a deterministic reference generator) is separate
   work and is not attempted here.

## The `.md.deps` rule no longer sees post transclusions, and that is correct

Step L3 extended the Makefile's dependency-extraction `sed` to capture `orgit:`
link targets so a post would rebuild when its transcluded source changed. That
pattern does not match the `orgit-file:…::TAG::path::uuid` form pinning
introduced, so pinned posts now generate `.md.deps` files naming only the `.org`
itself.

Do not "repair" this. A pinned post's code comes from an immutable tag, so it
has no worktree dependency to track: rebuilding it when the working tree changes
would be the bug, not the fix. The L3 rule stays useful only for
`docs/compiler_architecture.org`, the one living document that still resolves
against the worktree. A third encoding of a `&mdash;`-style HTML entity or an
`#orgXXXXXXX` id may still differ run to run (see above); that is export churn,
not drift, and is not worth committing.
